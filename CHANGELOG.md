## [Unreleased]

### Added

- `GET /api/assets/materials/{guid}/shader-compatibility` reports where a material and its shader disagree, which is the question a client has after editing a shader and which nothing answered. `GET /api/assets/materials/{guid}` reports the properties the shader currently declares with the material's values, and `GET /api/assets/shaders/{guid}` reports what the shader declares; both walk the shader's declarations, so a value the material still carries for a property the shader dropped appears in neither. Unity does not discard that value — it stays in the `.mat` file and is hidden from the Inspector — so a renamed shader property makes the old value look simply lost, with nothing to say where it went. `staleProperties` is that answer and carries the value as well as the name, so the report is "here is what you would lose" rather than only "something would be lost": measured on 6000.0.80f1 against a material created from a shader declaring `_Extra` and then reimported after the declaration was removed, `m_SavedProperties.m_Floats` still held `_Extra` at `42` while `Material.HasProperty("_Extra")` answered `false`. Two edits strand a value and only one is about the name, so the check compares each stored entry against the declaration that would read it rather than asking whether the name survived: measured on the same version with `_Extra` redeclared from `Float` to `Color`, `m_Floats` still held `_Extra` at `42` while `GetColor("_Extra")` answered the new declaration's default — so the `42` is as lost as a dropped property's value while the shader still declares the name. A property whose every stored entry is unreachable appears in `unsetProperties` as well, because it then has no value the shader can read either. `Float` to `Int` is that same type change and is treated as one: an `Int` declaration reads `m_Ints`, and `m_Floats` is accepted for it only when the material's serialization carries no `m_Ints` map at all, which is the older format rather than a retyped property. The condition is the map's existence and not whether it holds the name, because Unity writes the entry for a newly reachable property lazily and the name is briefly missing from a map that does exist. Measured on 6000.0.80f1 with `_N` redeclared from `Float` to `Integer`, `m_Ints` gained `_N` at the declared default while `m_Floats` still held `_N` at `7.5` and both `GetInteger("_N")` and `GetFloat("_N")` answered `0` — so accepting `m_Floats` for every `Int` would take that `7.5` for the live value and report the pair as agreeing. `unsetProperties` describes the material as it is serialized at the moment of the call and the reference says so, because Unity writes the entry for a newly reachable property lazily: measured across two calls against the same unmodified material after that same retype, the first reported `_X` in both lists because no `Color` entry existed yet and the second reported it only as stale, Unity having written that entry in between. `staleProperties` is unaffected either way. A stale texture reports the reference together with the `scale` and `offset` stored beside it, because all three are lost together. `storage` says which map in the material's serialization held the value — `Texture`, `Int`, `Float` or `Color` — and is deliberately not called a type: the declaration naming the type is what is gone, and the storage does not preserve it. Measured on the same version, `Float` and `Range` both land in `m_Floats` and `Color` and `Vector` both in `m_Colors`, so a stale `Vector` is not distinguishable from a stale `Color` and the reference says so rather than guessing. `unsetProperties` is the opposite direction, with the `type` and `defaultValue` the shader declares so that finding out does not take a second call. It is empty for a pair that has not drifted, because Unity writes an entry for every declared property when the material is created; it fills when the shader gains a property afterwards, which is not broken — the material uses the declared default — but was nobody's decision, and the material read cannot tell that apart from a value someone chose. `invalidKeywords` is checked against the shader's effective local keyword space, the same one the shader read reports: Unity does not prune a material's keywords when its shader changes, so a material keeps claiming a keyword that no longer exists and nothing said so. Measured on 6000.0.80f1, a material with `UNIONAIR_PROBE_ON` enabled still reported it in `Material.shaderKeywords` after its shader was reimported with that keyword renamed. A keyword absent from that space is genuinely unusable; a keyword present in it is not evidence that the shader's author declared it, which is not answerable through public API at all, and the reference says so rather than letting the field imply otherwise. The endpoint reports and never writes. Dropping a stale property is a write to the material whose consequence is discarding the very value a client may be trying to recover, so it does not belong behind a read. It also refuses rather than answering when the shader cannot support a comparison, because a shader Unity substituted declares no properties and comparing against one would report every value the material carries as stale — the exact opposite of the truth, and indistinguishable from a real answer. `comparable` is `false` with a `reason` of `shaderMissing` when the material's shader was replaced by Unity's internal error shader, which is what a deleted or unassigned shader looks like — measured on 6000.0.80f1, both routes read identically, with `name` `Hidden/InternalErrorShader`, no recorded error, and zero properties, so the shader read's own "was this read" rule does not catch it and it needed its own test — and `shaderNotRead` when the ShaderLab parse failed before the shader's name was read, which is the rule the shader read already uses and which is now shared between them rather than written twice. The three lists are `null` together there, so `comparable` is the one thing a client has to check, while the `shader` block is still reported because which shader the material ended up on is most of the answer in that state. A `Fallback` is not one of those cases: it replaces the compiled subshaders and not the declared properties, so the comparison stays sound. It is a separate endpoint rather than a section on either read because the question is about a pair that neither read owns, and because a client that never asks should not pay for the comparison.
- `GET /api/assets/shaders/{guid}` and `GET /api/assets/shaders?name=` read a shader: its import state, the compiler messages Unity cached for it, its effective local keyword space, every property it declares with the default a new material would start at, and the subshaders Unity compiled. Writing shader source stays with the client, and this endpoint does not take it over — two things are simply not in the file. The first is whether Unity accepted the import: shader compilation happens as the asset is imported, a shader that failed sits on disk looking exactly as it did, and the only report was Console text a client had to recognise and attribute by hand. `hasError`, `hasWarnings`, and `messages` close the edit-import-diagnose loop for shaders the way `POST /api/compile` closes it for C#, and each message keeps its `severity`, `file`, `line`, and `platform` rather than being flattened into a string — the platform is why the same edit can fail on one graphics API and pass on another, which a single string cannot say. The second is what the import produced: `activeSubshaderIndex` is decided by the current render pipeline and platform and is written nowhere, and a `.shadergraph` states none of its properties, keywords or passes in its file at all, because they are generated during import — which is exactly why the read answers them. A Shader Graph needs no separate endpoint and gets no special case: Unity's importer makes the generated shader the asset's main object, so the same read reports it. Measured on 6000.0.80f1 with Shader Graph 17.0.4 and URP 17.0.4 against a graph carrying one blackboard property, it reported that property with its default beside the ones Shader Graph generates, the URP subshader's ten passes with their `lightMode`, and a 60-keyword space. The generated `name` is the part worth having: it is the graph's category joined to the file name, the file carries only the category, and that name is what a material stores and `POST /api/assets/materials` takes. Each subshader also reports its `RenderPipeline` tag as `renderPipeline`, which is what answers "is this a URP shader, an HDRP one, or a built-in one" — the first question when picking a shader for a material, and one that is per subshader rather than per shader, since a single file can carry a URP subshader and a built-in one and only the tag tells them apart. It is `null` when the subshader declares no such tag, which is how a built-in-pipeline subshader reads and how `lightMode` already reports an absent tag. Tags are named fields rather than a `tags` map because Unity looks a tag up by name and offers no way to enumerate the ones a subshader or pass carries, so a map could only ever hold the keys the endpoint thought to ask for while reading like the whole set. The property half also answers a question the material read cannot: `GET /api/assets/materials/{guid}` reports the properties of a shader a material already uses, so a client choosing a shader for a material it has not created yet had nowhere to ask what that shader declares. `defaultValue` is spelled the way `PATCH /api/assets/materials` reads it, so an untouched property is distinguishable from a deliberate one; a `Texture` reports its built-in texture name (`"white"`, `"bump"`) rather than an object reference, because that is what the declaration carries and no asset exists to point at. `keywords` is the shader's effective local keyword space rather than the enabled set, which is the one a material stores and the one the material read already reports. "Effective" is the load-bearing word and the reference spells it out: the space also carries keywords reached through `Fallback` and `UsePass` dependencies and keywords Unity adds by itself, so a name appearing there is not evidence that it appears in the file — measured on 6000.0.80f1, a shader declaring exactly one keyword through `multi_compile` reports five, the other four being stereo keywords its source never mentions. `attributes` carries the declaration attributes Unity did not turn into a flag, verbatim and with their arguments: measured on 6000.0.80f1, `[HideInInspector]` and `[MainTexture]` arrive in `flags` and never appear in `attributes`, while `[Toggle(_X)]` has no flag at all — so without this field a client reading a shader cannot say which property drives which keyword. `flags` is produced by the same helper as the material read, so the two endpoints cannot drift apart. The lookup by name exists because a name is what a material carries and what `POST /api/assets/materials` takes, and it answers `404` for exactly the names that endpoint would fail on, which is worth finding out before the material is created rather than after. It is also the only way to reach a shader Unity ships rather than one the project owns: measured on 6000.0.80f1, `Standard` reports `Resources/unity_builtin_extra` and the GUID every built-in asset shares, and sending that GUID to the GUID lookup answers `400 Asset is not a Shader` because the container's main asset is not one. That is reported as it is rather than papered over with a `null`. `messages` is the set Unity currently has cached and not a fresh compile, which the reference says plainly; a reimport through `POST /api/assets/reimport` clears it and refills it with what that import compiled. It also grows without one, because Unity compiles variants on demand — measured on 6000.0.80f1, an error inside a `multi_compile` keyword's branch is absent right after the reimport and present once the Scene View renders a material enabling that keyword, and reimporting clears it again. So a clean `hasError` means nothing has compiled a broken variant yet rather than that the shader is valid, and an error appearing in a later read with no edit in between is a variant reaching the compiler for the first time. That call and this read are the whole edit-import-diagnose loop and no validation endpoint is added beside them, because one would report the state at the moment it ran and that is not a verdict on the shader. A caller that needs the import to have settled before reading is pointed at `isUpdating`. Diagnostics arrive from two places and both are reported, side by side rather than merged: `hasError` and `messages` are the shader compiler's, `hasImportError` and `importMessages` are the asset importer's, read from `AssetImporter.GetImportLog`. The second set exists because of what a generated shader does when it fails — measured on 6000.0.80f1, a Shader Graph the importer cannot build is replaced by Shader Graph's own error shader renamed to the name the graph would have had, and that substitute compiles cleanly, so `hasError` is `false`, `messages` is empty, and nothing else in the response distinguishes it from a shader that declares little. The two logs do not overlap: a ShaderLab parse error fills `messages` and leaves `importMessages` empty, because `ShaderImporter` does not use the import log. `null` is not `[]` here either — `[]` is an importer that recorded nothing, `null` is no importer to ask, which is how a shader Unity ships reads. The limit is documented rather than papered over, because a clean `hasImportError` is not proof of a clean import: a target that does not resolve reaches neither log and only the Console, since Shader Graph writes that one with `Debug.LogError` instead of through the import context, and a graph that parses and cannot be built reaches nothing at all — not the compiler's log, not the importer's, not the Console. The reference carries the boundary as a table and marks which rows were measured. A guid whose asset produced no shader at all is no longer a dead end either: it still answers `400`, but says `Shader asset failed to import` rather than `Asset is not a Shader` when the importer failed, and carries the importer's log either way, only the sentence in front of it changing. That second wording needs an import error and a `.shader` or `.shadergraph` extension together, because every importer writes to the same log and an import error alone does not make an asset a shader — a `.png` Unity could not read fails its import and types as a `DefaultAsset` exactly like a broken graph. `importMessages` carries `file` and `line` as Unity gives them, and unlike `messages[].file` that is not necessarily a file in the project: measured on 6000.0.80f1, a native importer's entry pointed at Unity's own C++ source, a path on the machine that built the editor. The structural fields are `null` in exactly one case, and it is deliberately narrow: the ShaderLab parse failed before the shader's name was read, so nothing in the response could have come from the file. Measured on 6000.0.80f1 against a shader declaring one property and one pass that failed that way, `name` read `""`, `properties` read empty, `keywords` listed four stereo keywords the shader never declared, and `passCount` read `3` against the one pass in the file — none of it distinguishable from a real answer, and a client building a material from `properties` would build one with no properties and never learn why. `renderQueue`, `maximumLOD`, `subshaderCount`, `passCount`, `keywords`, `properties`, `activeSubshaderIndex` and `subshaders` are `null` together there, leaving `messages` as the answer; every other shader reports the structure Unity exposes for it, including one that fails to compile and one that cannot run here — the declaration for `properties` and `name`, and for `subshaders` what Unity compiled, which can be a `Fallback`'s. Neither `isSupported` nor `hasError` is that rule, and the reference says what each does mean. `isSupported` is Unity's capability signal — whether the shader runs on the current GPU, fallbacks considered — and measurements on 6000.0.80f1 show it settling both ways for reasons unrelated to the import: a shader with no errors whose only pass is excluded for the current renderer reports `false` while its properties are perfectly readable, and the same shader given a `Fallback` reports `true` while its `subshaders` become `Legacy Shaders/Diffuse`'s, two subshaders and four passes identical to reading that shader directly. `hasError` is not a usability signal either: a shader whose first subshader fails to compile and whose second does not reports `hasError` true, `isSupported` true, and Unity draws with the working subshader. Absence is `null` rather than `""` throughout, for the same reason: a pass the shader did not name, a message with no file, and a parse error's platform — which Unity reports as an undefined enum value whose `ToString` is `"-1"`, a number in a field documented as an API name. Editing shader source over REST, Shader Graph authoring, and `ShaderVariantCollection` remain out of scope.

## [0.6.0] - 2026-08-16

### Upgrade Notes

- An object reference names one object inside a file with `localIdentifier`, and a write that cannot name the object it would resolve answers `400` instead of `200`. `assetGuid` and `assetPath` identify a file, and a file and a type together are not an identity: measured on 6000.0.80f1, a character model holds 23 meshes, every renderer on it read back the same `{assetGuid, assetPath, assetType}`, and `PATCH` against that reference answered `200` having bound whichever mesh `LoadAssetAtPath` returned -- `BLW_DEF`, chosen by nothing the client said. A read-modify-write on such a model could silently swap a mesh, and the read afterwards could not show it. Reads now report `localIdentifier`, the object's local file id as a decimal string, on **every** asset reference including single-object ones, so a response's shape never depends on what it points at; the spelling is the one `GET /api/assets/model-importer/{guid}` already used for the same concept. Writes take it as optional and resolve three ways: with it, that object; without it against a path holding one object of the required type, that object, which is most references and is unchanged; without it against a path holding more, `400` naming the candidate count. That third case is the breaking one, and no client can have depended on it deliberately -- it was never choosing. The same change closes the loud half of the same gap: a built-in resource -- the mesh on a primitive, in `Library/unity default resources` -- carries a GUID and a file id like anything else, so reading one and sending it straight back now resolves where it answered `404 Asset not found or incompatible`, and no separate spelling for built-ins was needed. `GET /api/assets/{guid}` gains `subAssets` so the identifier is discoverable; built-in containers are the exception and are not listed, so the way to obtain one of those is to read an existing reference to it. A client that sent a bare `{assetPath}` for a mesh inside a model must now send `localIdentifier` alongside it.

- `GET /api/gameobjects` reports an object reference in `components[].properties` in the vocabulary `PATCH /api/gameobjects/components` accepts, where it previously reported `{type, name, globalObjectId}` — a shape that endpoint refused. Measured on 6000.0.80f1, reading a `MeshFilter` and sending the value straight back answered `400 Unknown field 'name'`, and dropping `name` answered `400 Unknown field 'globalObjectId'`, so a client could not read a component, change one field, and send the result back without rewriting every reference in the body first. An asset is now `{assetGuid, assetPath, assetType}` -- joined by `localIdentifier` in the entry below, which landed after this one -- and an object in a loaded scene is `{"type": "globalObjectId", "value": ...}`, both of which the write already resolved. `type` was the sharp edge and is the part to check when migrating: it carried the object's class in the read and the kind of reference in the write, so a client echoing a read was told its type was unknown about a field it never meant to fill in. It now has the write's meaning at both ends, and the class — for assets, which are the only references that carry one — is `assetType`, spelled fully qualified (`UnityEngine.Mesh`) where the old `type` was short (`Mesh`). The display name is gone: no field of the write carries one, and keeping it would mean the write either refusing the read again or accepting a key it ignores, which is the silence removed from `properties` elsewhere in this release. A client that read `properties.<ref>.name` must resolve the reference to name it, or read `assetPath`; a client that read `.globalObjectId` reads `.value`; a client that read `.type` as a class name reads `.assetType`. This also settles a disagreement inside the package: `GET /api/assets/scriptableobjects/{guid}` already reported `{assetGuid, assetPath, assetType}`, so the same value had two spellings depending on which read produced it, and now has one. Two limits are unchanged and now written down rather than discovered: an object in a scene that has never been saved has no `GlobalObjectId` and cannot be addressed by one, and a built-in Unity resource is addressed by GUID and file id together, which this shape had no room for. That second limit is lifted by the `localIdentifier` entry below, which ships in the same release; a built-in reference read from this endpoint resolves when sent back.

- `PATCH /api/gameobjects/components` and `PATCH /api/assets/scriptableobjects` answer `400` for a key in `properties` that updated nothing, where both previously answered `200` with that key missing from `updated`. Three shapes reached that silence and none was visible to a client: a key naming no serialized property, a value of the wrong shape, and a key naming a property the endpoint does not write. Measured on 6000.0.80f1 before the change, `{"decoy":1}` and `{"m_Materials":[]}` answered `200 {"updated":[]}` against a `Camera` and a `MeshRenderer`. Every other shape reaches the same silence by the same path -- the typed reader answers null, the apply returns false carrying no error, and the loop moves on -- and each is measured against the change instead: `{"near clip plane":"0.5"}` answers `Property near clip plane expects a JSON number.`, `{"orthographic":"true"}` answers `Property orthographic expects a JSON boolean.`, and `{"m_BackGroundColor":1}` and `{"m_NormalizedViewPortRect":{"x":0,...}}` name the member shape and the unwritable serialized type. The quoted number and quoted boolean are the ones that will have been hit in practice: a client that JSON-encodes its scalars as strings received a success response for a PATCH that changed nothing at all. Each now answers `400` naming the key and saying which of the three it is, so `updated` always lists every key the request sent and a `200` means the whole request was applied. An empty `properties` object is still `200`, because nothing was sent and so nothing is unaccounted for. A client sending keys these endpoints never applied must drop them; a client that trusted `200` has to fix requests that were already not doing what they said. "Array and nested generic properties are silently skipped" is withdrawn from the ScriptableObject reference along with the behaviour it described, and `Quaternion`, `Rect` and `Bounds` -- serialized by the read direction and never written by this one -- are refused by name rather than passed over. `m_Script` is refused the same way, on the two kinds of object that have one: a MonoBehaviour component and a ScriptableObject asset. Arrays reached that silence too, and are now writable rather than merely reported -- see the entry under Added.
- `PATCH /api/assets/materials` answers `400` for a key in `properties` that it did not write, where it previously answered `200` with that key missing from `updated`, and a texture is now named by the object reference the rest of the package uses rather than by `{"guid": ...}`. Three shapes reached the old silence and none was visible to a client. A key naming no property on the material's shader was never examined at all, because the walk enumerated the *shader's* properties and asked whether each name occurred somewhere in the request body, rather than enumerating what the request sent: measured on 6000.0.80f1, `{"_NoSuchProp":1.0}` answered `200 {"updated":[]}`. A texture sent as the GUID string this endpoint's own documentation described, and a texture sent as the `{"assetGuid": ...}` reference every other write accepts, answered the same thing -- only `{"guid": ...}` stored anything, and that shape appeared in no document. And the two combine in bulk: a request carrying five texture keys and three colour keys answered `200 {"updated":["_BaseColor","_1st_ShadeColor","_2nd_ShadeColor"]}`, three of eight applied, no error field, and the only way to notice was to already know that `updated` is not an echo of the request. `updated` now always lists every key the request sent, and a `200` means the whole request was applied. A key that names no shader property, repeats another key, or carries a value of the wrong shape for its property type answers `400` naming the key and which of those it is, and the material is left exactly as it was, because the request is resolved completely before the first value is applied. A client sending `{"_MainTex":{"guid":"..."}}` must send `{"_MainTex":{"assetGuid":"..."}}` or `{"assetPath":"..."}`, optionally with `assetType`; a client sending a bare GUID string, or keys this endpoint never applied, was already not getting what it asked for and now finds out. A `Color` or `Vector` value follows the same rule one level down, matching what the component and ScriptableObject writes already enforce: an omitted component still keeps the material's current value, and an unknown, duplicate or non-numeric one -- `{"_BaseColor":{"r":"1"}}`, the quoted number a client gets from JSON-encoding its scalars as strings -- answers `400` where it was previously read as "not a number" and passed over, taking the whole value with it. An object carrying no component at all is refused for the same reason. `GET /api/help` described the old shape too, in the endpoint's summary and request example, and now describes the new one.
- `POST` and `DELETE /api/assets/animation-clips/{guid}/curves` refuse a clip generated by a `ModelImporter` with a `409`. They accepted the write before and answered `200`, and the next reimport discarded it -- a silent data-loss path, and the ordinary case rather than an edge one, since a character's animation set usually arrives as `.fbx`. A client writing curves to an imported clip was never getting what it asked for; it now finds out. Writing to a `.anim` clip is unchanged.
- `GET /api/assets/animation-clips/{guid}` gains `name`, `clipsAtPath`, `clipNames`, `imported`, `importer`, `writable`, `settings`, and `events`. Nothing was removed, but a client that assumed the response described one clip should read `clipsAtPath`: a path holding several takes exposes one by GUID and hides the rest.

- `POST /api/assets/animator-controllers/{guid}/parameters` no longer moves an existing parameter to the end of the parameter array. It used to remove and re-add on every call, so changing a default value reordered the Animator window's list for a change meant to be invisible. A parameter with the same type is now updated where it sits; only a type change still destroys and recreates it. A client that relied on the reordering -- there is no reason to have -- must reorder in the Animator window instead.
- `DELETE .../parameters` answers `{"removed": ..., "orphanedReferences": n, "references": [...]}` instead of `{"removed": ...}` alone. The delete is unchanged; the response now names what it broke.

- `GET /api/assets/animator-controllers/{guid}` replaces each transition's `to` string with a `destination` object carrying a `type` of `State`, `StateMachine`, `Exit`, or `None`. A destination may now be a state machine, and a name alone cannot say which it is: `"Melee"` is a state in one controller and a sub-state machine in another. A client reading `transitions[].to` must read `transitions[].destination.type` and, where it applies, `destination.name`. The request side is unchanged -- `from` and `to` still address by name, and `transitionId` still addresses exactly one.
- A layer whose states live inside a sub-state machine no longer reports `"states": []`. Those states are now under `layers[].stateMachines[]`, recursively. A client that walked `layers[].states` and concluded a layer was empty was reading a controller it could not describe; it now has to walk `stateMachines` too.

- `POST` and `PATCH /api/assets/animator-controllers/{guid}/states` reject a request body carrying a field they do not recognise, with a `400` listing the accepted ones. They previously ignored it, so `writeDefaults` instead of `writeDefaultValues` -- a plausible typo now that the field exists -- would have returned `200` having changed nothing. A client sending fields these endpoints never accepted must drop them.
- `behaviours` is accepted by both endpoints and not applied. It is a field of the read, so a client round-tripping a state sends it back and must not be answered "unknown field"; it is named in the response's `unsupported` array instead. Attaching a `StateMachineBehaviour` remains out of scope.

- `GET /api/assets/animator-controllers/{guid}` reports `motion.guid` as `null` for a state whose motion is a blend tree, where it previously reported the controller's own GUID. Read `motion.type` to tell the two kinds apart. A client that passed those GUIDs to `GET /api/assets/animation-clips/{guid}` was already receiving a `400`; a client that used them to identify the controller was relying on an accident.
- `DELETE /api/assets/animation-clips/{guid}/curves` answers `400` for a `property` that names no binding on the clip, where it previously answered `200` and listed that name under `removed`. This affects a client that sent the name it wrote rather than the name `GET` returns -- `localPosition.y` instead of `m_LocalPosition.y` -- which is the spelling this endpoint's own documentation used as its example. No such request ever removed a curve, so nothing that worked stops working; what changes is that the failure is now visible to a client that reads the status code rather than the body. Send the serialized property name that `GET /api/assets/animation-clips/{guid}` reports.
- `POST /api/assets/animation-clips/{guid}/curves` answers `400` for an entry that stored none of its keys, where every such request previously answered `200` with an empty `errors` array. `AnimationClip.SetCurve` selects a Transform group by the property name's prefix and the component that carries the keys by its suffix, so a suffix naming no component of that group -- `m_LocalPosition` with none at all, or `m_LocalPosition.w`, which is the plausible spelling because the quaternion group does have a `.w` -- leaves the keys nowhere to land. Measured on 6000.0.80f1, both created `m_LocalPosition.x/.y/.z` carrying no keys whatever, and the response listed three bindings and no error for a clip that animates nothing. The check reads what the entry alone would store rather than what the clip ends up holding, because against a group that already carries curves the same write is a complete no-op: the keys already there survive and pass a check made afterwards, while the keys the request sent are dropped just the same -- the worse of the two shapes, since the caller believes it replaced the curve. The status now turns on whether any entry stored what it was asked to rather than on whether the clip gained a binding, which is what let the original request through: the group write creates the group, so bindings were added. A request mixing a good entry with a bad one still answers `200` and reports the bad one. A client sending a group name without a component, or with one that is not part of it, was never getting the curve it asked for and now finds out; send the exact component.
- The same endpoint gains a `warnings` array, always present and empty when there is nothing to report, carrying a write that landed but is probably not what was meant. It has one member today: an `m_LocalRotation` group left non-unit at the times it is keyed. `SetCurve` fills the components a request does not name with `0` and the quaternion identity is `w = 1`, so a single entry on `localRotation.y` stores `(0, y, 0, 0)`, which normalizes to a half turn whatever `y` holds -- measured, a request for 90 degrees played back 180. This is a warning rather than an error because the write did store a curve, and because a caller may fill the quaternion in over several requests: a later write to another component replaces that component and leaves the ones already carrying curves alone (measured), so such a caller is warned on every request but the last, and on each of those the clip really does hold a rotation that plays back wrong. A completed quaternion is not reported, whether it arrived in one request or four. The check catches more than the missing `w`: a group write resamples every component onto the union of the group's key times, so a component keyed at `0` and `2` receives an interpolated value at `1` -- against a `y` of `0.7071` that is a `w` of `0.5` and a rotation of 109.5 degrees where 90 was meant. Only the key times are checked, because a correctly authored quaternion is not unit length between them either. A client reading the response by field name is unaffected; one that compared it whole must account for the new array. Write rotation as `localEulerAngles.*` unless you are sending all four quaternion components deliberately.
- `POST /api/assets/animation-clips/{guid}/curves` reports serialized binding names in `added`, `addedFloat`, and `addedObjectReference`, where it previously echoed the `property` each entry sent. A request writing `localPosition.y` answered `{"added":["localPosition.y"]}` and now answers `{"added":["m_LocalPosition.x","m_LocalPosition.y","m_LocalPosition.z"]}`, because that is what the clip holds. A client that matched the response against the names it sent must read the new per-entry `curves[]` and `objectReferenceCurves[]` arrays instead, where `requested` is the name it sent and `bindings` the names that resulted. Nothing about the write changed; only the report did. The names are the ones `GET` returns and `DELETE .../curves` accepts, so a write and a delete now compose without a read between them.
- `DELETE /api/assets/animator-controllers/{guid}/transitions` addressed by `from` and `to` no longer removes every transition between that state pair. It removed all of them through `RemoveAll` and reported the same `{"removed":true}` it reports for one, so a client deleting "the Idle to Walk transition" could destroy four others it did not know existed and read a success identical to the one-transition case. It now removes one, or answers `409` listing every match. A client that relied on the bulk behavior must send one request per `transitionId`.
- `PATCH /api/assets/animator-controllers/{guid}/transitions` addressed by `from` and `to` no longer updates the first of several. The same pair now answers `409` with the candidates, and `transitionId` addresses one unambiguously. A request against a pair that carries one transition is unaffected.
- Both endpoints accept `transitionId` in place of `from` and `to`, so neither is a required field any more. A request carrying neither address answers `400`.
- `conditions: []` on `POST` and `PATCH .../transitions` now clears the transition's conditions. It previously meant "leave them alone", which was indistinguishable from omitting the field and left no way to remove the last condition. Omitting `conditions` still leaves them unchanged.
- A condition whose `mode` is not one of `If`, `IfNot`, `Greater`, `Less`, `Equals`, `NotEqual` is now rejected with `400`. It was previously skipped, so a request listing three conditions could store two and report success. A `threshold` that is present but not a number -- a quoted `"0.5"`, a `null`, a `NaN` -- is rejected for the same reason: it previously read as `0`, so a `Greater` condition could be stored with its threshold moved to zero and the response would say the write succeeded. An omitted `threshold` is still `0`, which is the value `If` and `IfNot` use.
- `GET /api/assets/animator-controllers/{guid}` renames the layer field `weight` to `defaultWeight`. The old name invited the reader to believe it was the weight in effect, and on the base layer it is not: layer 0 runs at 1 whatever the field holds, so a freshly created controller reported `"weight": 0` on a fully active layer. A client reading `layers[i].weight` now gets nothing rather than a misleading number, which is the intended outcome. `POST .../layers` still accepts `weight` in the request body, since a request field naming what it sets was never ambiguous.

### Changed

- `GET /api/assets/animator-controllers/{guid}` now says what each motion is, and describes blend trees instead of pointing at them. A `Motion` is either an `AnimationClip` or a `BlendTree`, and the previous response serialized both as `{guid, name}` with the GUID taken from the containing asset -- so a blend tree reported the controller's own GUID, and nothing in the response distinguished it from a clip. Following that GUID reached a `400` from the clip endpoint, which was the only way to discover the motion's kind and cost one request per state. Every motion now carries a `type` of `AnimationClip`, `BlendTree`, or `Unknown`; a blend tree carries a `null` GUID, because no GUID addresses a sub-asset, and its `blendType`, blend parameters, thresholds, and children are serialized inline, recursively, so a nested tree is described like any other. Nesting is serialized to a depth of 10, and a tree at that depth is marked `truncated` with no `children` rather than being presented as childless. `Unknown` is a forward-compatibility branch for a `Motion` subclass this version does not describe, and reports a GUID only when the motion is the main asset at its path, so an unknown sub-asset cannot report its container's GUID the way a blend tree used to; a motion whose asset was deleted still reports `null`, since Unity resolves a missing reference before its type can be examined.
- A clip motion now reports `assetPath` and `clipsAtPath` alongside its GUID, because the GUID is not always as precise as it looks. A clip imported from a model file lives inside that file, so the GUID identifies the file rather than the clip -- which is the ordinary case, since a character's animation set usually arrives as `.fbx` rather than as `.anim` assets. When `clipsAtPath` is greater than 1 the GUID cannot address one take, and the client can now see that rather than discovering it by fetching the wrong clip. Addressing an individual clip inside an imported file is not done by GUID and belongs with the ModelImporter work, which ships in this same release: `GET /api/assets/{guid}` reports each clip under `subAssets` with its `localIdentifier`, and `GET|PATCH /api/assets/model-importer/{guid}` addresses each take's definition -- reported under `settings.clips.definitions` and replaced through the top-level `clips` array.

### Added

- `GET /api/assets/materials/{guid}` reads a material: its shader name, render queue, enabled keywords, and every property its shader declares, each with a `type`, its current `value`, the `range` limits of a slider, and Unity's shader property `flags`. The write had no matching read, so a client could set `_BaseColor` and had no way to ask what `_BaseColor` was — or what it is on the material it is trying to match. Reading the `.mat` file is not the alternative it looks like: that file serializes the overrides Unity recorded rather than the effective values, a property sitting at its shader default has no entry in it, and the property set and its types come from the shader, which only Unity can enumerate. Making a variant of an existing material — the ordinary way a colourway is authored — therefore meant opening the `.shader` file for property names and rebuilding every value by hand. Every `value` is spelled the way `PATCH /api/assets/materials` reads it, so a read, a change, and a write back is a round trip that holds; measured on 6000.0.80f1 against a 278-property material, echoing the whole read back answered `200` with all 278 keys in `updated` and left every value identical. That only became possible with the material write's own change earlier in this release, which took the package's object reference for a texture and accepted `Int` and `null`. `properties` is an array rather than a name-to-value map because `type`, `range` and `flags` have nowhere to live in a map, and they are the part only Unity can answer; the write takes a map, and every `name` here is a key it accepts. `renderQueue` and `keywords` are reported and not writable, which the reference says plainly: they are usually why a material built from another one's property values still does not look the same, and naming them is more useful than the silence. Texture scale and offset are not reported, because they are not shader properties of their own and the write has no vocabulary for them.
- `GET /api/gameobjects` reports `worldTransform` beside `transform`, and `bounds` on a `Renderer` component. Every transform the API reported was parent-relative, and composing one up the chain by hand was not open either: `m_LocalRotation` reads `null` on every Transform (#122), so the rotations the composition needs are the ones missing. The workaround that existed was to create marker objects under the target, reparent them to the scene root — which preserves world pose — read their positions and subtract: four creates, four reparents, four reads and four deletes to learn where one bone is and which way it faces, mutating the scene to ask a read-only question. `worldTransform` carries `position`, `rotation`, `lossyScale`, and the object's own `right`, `up` and `forward` as unit vectors in world space. The basis vectors are the half that makes it usable rather than merely correct: measured on 6000.0.80f1, a humanoid head bone's local `+X` points **down** in world space, which `right` says directly and which `(359.43, 267.51, 277.86)` says only after the reader redoes Unity's quaternion-to-basis conversion — the reimplementation this package exists to avoid. `lossyScale` keeps Unity's name because it is derived from the whole chain and cannot be written back, where `scale` would invite a client to echo it into a `PATCH` that means the local value. `bounds` is `Renderer.bounds`, the world-space AABB, as Unity's own `center` and `extents`; the serialized `m_AABB` in `properties` is the local box and a different value, and there was previously no way to ask how large a renderer is — `POST /api/previews/render` computes exactly this to frame its camera and reports none of it. Three things are deliberately unchanged and say so in the reference: `GET /api/scene/hierarchy` does not report the world transform, because it walks a whole scene and six vectors per node is a cost every caller would pay for a value wanted one object at a time; `PATCH /api/gameobjects` stays local-only, because a child's transform is authored in local space and knowing the parent's frame is what a placement needs; and there is still no aggregate box for a GameObject and its children.
- `GET /api/gameobjects` reports `blendShapeNames` on a `SkinnedMeshRenderer`, beside `properties` rather than in it. `m_BlendShapeWeights` was readable and writable as a bare array of numbers, and nothing in the API said which shape each slot drove, so identifying one meant writing `100` into an index and rendering the result -- eleven writes and eleven renders for a face mesh with eleven shapes, and an answer that a reimport reordering them silently invalidates. The names are the mesh's, read through `Mesh.GetBlendShapeName`, and they sit outside `properties` for the reason `enabled` does: a shape name is not a serialized field of the renderer, and reporting it as a property would announce a key `PATCH /api/gameobjects/components` then has to refuse. The array is positional, in mesh order, so index *i* names the shape `m_BlendShapeWeights[i]` drives -- which is also how a weight is written. Names are deliberately not the identity: Unity permits two shapes on one mesh to share a name, so a name-keyed object would lose one, and writing by name would be ambiguous. The field is omitted for every other component type, and is present and empty both for a mesh with no blend shapes and for a renderer with no mesh, which `m_Mesh` already tells apart. The two arrays can disagree in length -- the names come from the mesh as imported now and the weights from what was serialized on the component -- and neither is corrected to match the other, which is documented rather than papered over.
- `PATCH /api/assets/materials` writes `Int` shader properties and clears a texture with `null`. Neither had a case in the writer, so both were dropped in the silence removed under Upgrade Notes. The two integer spellings a `Properties` block allows do not land in the same place, which is worth knowing before reading a shader and predicting the result: a property declared `int` is reported by Unity as `Float` or `Range` and always wrote normally, while only the `Integer` declaration produces `ShaderPropertyType.Int`. Measured on 6000.0.80f1 against `Toon/Toon`, `_AutoRenderQueue`, `_StencilMode`, `_ClippingMode`, `_CullMode` and `_SPRDefaultUnlitColorMask` are the first kind and wrote before this change; `_ToonMaterialVersion` is the second, and answered `200 {"updated":[]}` for a JSON integer, a JSON number, and an object alike. A shader property type this endpoint still cannot write — there is none in the current `ShaderPropertyType` set, and the branch exists for a type a later Unity adds — answers `400` naming the key and the type rather than passing over it.
- Serialized arrays are writable through `PATCH /api/gameobjects/components` and `PATCH /api/assets/scriptableobjects`. Both endpoints described an array completely and refused every way of changing one, so a property the read reports in full had no write direction at all — swapping a renderer's material, an everyday edit, was not a request this API could express, and the only alternative was writing the scene file by hand. Three keys now do it, all of them spellings Unity's own `SerializedProperty.propertyPath` produces: `m_Materials` replaces the array and resizes it to the JSON array's length, `m_Materials.Array.data[0]` writes one element without resizing, and `m_Materials.Array.size` resizes alone. An element value takes the shape a top-level property of its serialized type takes, so nothing new has to be learned to write one, and an element that cannot be applied is named by its own address — `{"m_Materials": [null, 5]}` answers `Object reference property m_Materials.Array.data[1] must be null or an object.` rather than blaming the array. Measured on 6000.0.80f1 against a `MeshRenderer`: growing `m_Materials` from one element to three answers `200` and fills the two new slots with a copy of the last element rather than with `null`, which is Unity's resize and is now documented rather than assumed; clearing with `[]` and replacing a three-element array with one both answer `200`. A whole-array write is a replacement and not a merge, because Unity keeps no identity per element and rewrites the array wholesale — the same reasoning the AnimationClip event array follows. Arrays whose elements are `Generic`, such as a `List<T>` of a serializable struct, stay unwritable through all three addresses and say so, naming the element type: the read serializes such an element as `null`, so replacing or dropping one would destroy content the caller has never seen, and growing alone is refused with the rest rather than leaving a resize that works in one direction only. Writability is asked of the array rather than of whatever it happens to hold, because judging by the contents makes it depend on the length: a caller clearing an empty list would be answered `200` and the same request against a list holding one element `400`, which is the state-dependent success these endpoints exist to not give. An empty array is grown by one to be read and put back, which no caller can observe, since nothing is committed until `ApplyModifiedProperties`. Element sub-paths such as `m_Materials.Array.data[0].name` are refused by name, which also closes a hole of its own: the property walk follows foldout state, so whether such a key was reachable depended on Editor UI unrelated to the request. Array addresses are resolved through the array rather than by that walk, which is why the ScriptableObject endpoint gains them too — it visits top-level properties only and answered `No serialized property named 'tags.Array.size'` for a key the component endpoint accepted. One request must not both set an array's length and write its elements; two element addresses are two independent writes and are accepted, but a length beside them answers `400` naming both keys, because which applies first is not a question worth deciding on a caller's behalf. An index past the end answers `400` carrying the current length, and a negative `Array.size` answers `400`. A length above 1,000,000 answers `400` as well, which is a bound on this endpoint rather than a claim about Unity: `Array.size` is the one write whose cost is not paid for in the request body — a whole-array write spends bytes on every element it asks for, while forty bytes can name two billion — and Unity allocates what it is told, so an unbounded one turns a mistyped length into a lost Editor session. `updated` still lists every key the request sent, `200` still means the whole request was applied, and a refused request still leaves the array exactly as it was.
- Completed the initial ModelImporter contract with full imported-clip definition replacement. GET distinguishes stored `clipAnimations` from effective definitions derived from `defaultClipAnimations`; PATCH validates take names, unique clip names, frame ranges, loop/root-motion/additive coupling, AvatarMask references, and AnimationEvents before replacing the ordered array in the existing one-reimport transaction. Compatibility metadata now names unavailable schema settings for the current importer and deliberately unsupported `rig.humanDescription` and clip curves.
- Extended the ModelImporter endpoints with typed material import settings, external Material remaps, and rig/Avatar settings. Remap and source-Avatar references use GUID plus decimal-string local identifier when a file contains more than one compatible object; every reference resolves before mutation, and duplicate source identifiers are rejected. Rig validation makes Avatar setup dependencies explicit, reports `rig.humanDescription` as an unsupported initial setting, and includes source Avatar, humanoid oversampling, optimization, and extra exposed transforms in snapshots and rollback verification.
- Added versioned ModelImporter core-setting inspection, preflight, and updates through `GET|PATCH /api/assets/model-importer/{guid}` and `POST /api/assets/model-importer/{guid}/preflight`. Responses normalize model, mesh, geometry, normal, and tangent settings and enumerate durable imported Mesh, Material, Avatar, and AnimationClip identities as GUID plus decimal-string local identifier while excluding transient previews. PATCH validates the complete staged state before one `SaveAndReimport`, skips unchanged requests, reports before/after state, sub-asset deltas and import diagnostics, and attempts to restore the original settings if reimport throws.
- A component's enabled state — the checkbox in its Inspector header — is now readable and writable. `GET /api/gameobjects` reports `components[].enabled`, and `PATCH /api/gameobjects/components` takes an `enabled` field beside `properties`; either field alone is a complete request, and a body carrying neither answers `400` where `properties` alone used to be required. Neither side could reach it before: `m_Enabled` is a real serialized field, but Unity draws it in the component header rather than in the body, and both endpoints address properties through the visible-property walk, which returns only what the body draws. A client could therefore neither see whether a `Renderer` was on nor turn it off, while `isActive` had covered the GameObject equivalent since the beginning. The state is found by looking for `m_Enabled` rather than by testing a base type, because there is no single one: `Behaviour`, `Renderer`, and `Collider` each declare their own `enabled`. A component that declares none has no field in the read and answers `400` to a write, so absent and `false` stay apart. Sending `m_Enabled` as a key in `properties` answers `400` naming the `enabled` field, rather than reporting a name that does exist as unknown. The write joins the request's undo group, so one request remains one undo entry. `GET /api/search/gameobjects` is unchanged: its `components` array lists types for filtering and does not describe them.
- Added isolated GameObject and animation preview rendering through `POST /api/previews/render` and its single-frame binary `/image` variant. A request copies a scene object, prefab, or imported model into its own preview scene; optionally evaluates an AnimationClip through an `AnimationClipPlayable`, an Animator state at normalized time, or a typed Animator parameter set; frames all eight Renderer-bounds corners against both camera axes; supplies a solid background and two shadowless directional lights; and returns the images together with rig type, resolved Animator state hashes and clips, applied/skipped bindings, exact bounds, camera pose, and lighting. Up to 16 times are rendered atomically in one scene, bounded by an aggregate-pixel limit. Every path closes the preview scene in a `finally`, admission is capped at eight culling-mask owners, and the source scene, selection, cameras, Animator assignments, assets, Undo history, and AnimationMode remain untouched.
- Added typed AudioImporter inspection and updates through `GET|PATCH /api/assets/audio-importer/{guid}`. Responses distinguish stored inherited defaults from Unity's platform-effective settings, publish the Editor's platform/codec compatibility catalog, and include final AudioClip metadata. Writes strictly preflight global fields, default sample settings, and atomic platform override creation/update/removal before one `SaveAndReimport`; unchanged requests skip the reimport, and completed imports return structured warning/error diagnostics. Preload policy is modelled inside default/platform sample settings to match Unity 6.
- `PATCH` and `DELETE /api/assets/animator-controllers/{guid}/layers`, so a layer is no longer write-once at creation. Both address the layer by `layerIndex` rather than by name, matching every other endpoint and avoiding a second addressing scheme for an object Unity does not require to be uniquely named. On `PATCH` every field but `layerIndex` is optional and an omitted field is left unchanged; `avatarMask` takes an object to set and an explicit `null` to clear, which are different requests. `POST .../layers` accepts the same settings, so a masked layer takes one request rather than a create followed by a patch, and a rejected setting takes the create back rather than leaving a half-configured layer.
- The layer read response carries `defaultWeight`, `isBaseLayer`, `avatarMask`, `iKPass`, `syncedLayerIndex`, and `syncedLayerAffectsTiming`. It previously described four of nine settings, so a masked layer was byte-identical in shape to an unmasked one -- a client could not tell that a layer affects only part of the rig, which is the most consequential fact about it. `avatarMask` is `null` or `{guid, name}`; a mask is an ordinary asset, so unlike a blend tree its GUID is fetchable.
- `GET /api/assets/animation-clips/{guid}` reports the clip settings and the animation events, and `PATCH .../animation-clips/{guid}`, `POST`, and `DELETE .../events` write them. The read described a clip with five fields and `AnimationUtility.GetAnimationClipSettings` appeared nowhere, so everything the Animation Inspector shows above the curve list was unreachable -- Loop Time, Cycle Offset, the root motion bake settings, the additive reference pose. `wrapMode` was not a substitute and was actively misleading: measured on 6000.0.80f1, an imported idle clip reports `"wrapMode": "Default"` while whether it loops is `settings.loopTime`, so a client reading `wrapMode` to answer "does this loop" got an answer about something else. Both are now reported next to each other. Events were absent too, which meant a clip authored entirely through this API could not carry a footstep, a hit frame, or a VFX spawn. The event array is replaced wholesale, because Unity stores it with no identity per entry and rewrites it that way; omitting the field is a `400` rather than a clear, and every element is resolved before any is written.
- The clip read says who owns the clip. `name` is the clip's own, which `assetPath` and `guid` never gave -- both identify the file, and inside an `.fbx` the file holds the takes rather than being one -- and `clipsAtPath` with `clipNames` reports when a path holds several, which `LoadAssetAtPath` otherwise hides by returning the first. `imported`, `importer`, and `writable` say, before a client attempts anything, that a clip's settings belong to a `ModelImporter`. Ownership is decided by asking `AssetImporter.GetAtPath` rather than by the file extension, since a `.anim` is imported too by an importer that does not own the clip's settings.
- `PATCH /api/assets/animator-controllers/{guid}/parameters` renames a parameter and rewrites every site that names it. There was no rename, and the workaround corrupted the controller: `RemoveParameter` does not touch anything referring to the parameter, and `AnimatorCondition.parameter`, a blend tree's `blendParameter` and `blendParameterY`, and a state's four `*Parameter` overrides are all plain strings rather than references Unity maintains. Measured on 6000.0.80f1: renaming through the `parameters` array renames the parameter and leaves every one of those strings naming what no longer exists -- the controller still loads, the conditions still serialize, and they never evaluate again. The rename now walks every layer, every nesting level of every state machine, and every blend tree beneath every state, which is why this waited for sub-state machine traversal: a rename that missed a reference would be worse than no rename at all. Each rewritten site is reported in `references` with its `layerIndex`, `stateMachinePath`, and the state, transition, or child path that locates it, because a count alone gives a caller nothing to check. `newName` colliding with an existing parameter is a `409`, and the rename is atomic: everything is collected and checked before the first write, so a refused request leaves the parameter and its references exactly as they were.
- `DELETE .../parameters` and a type change through `POST .../parameters` report the references they orphan, in the same shape. Both still go through -- what a condition should become without its parameter is not a decision this API can make -- but a delete that used to answer `{"removed": "Speed"}` whether the parameter was referenced by nothing or by forty conditions now says which.
- A `defaultValue` sent with `"type": "Trigger"` is reported in `unsupported` rather than dropped. Unity keeps no default for a Trigger, which is set and consumed within a frame; the endpoint used to discard the value and answer `201` exactly as if it had applied.
- Sub-state machines are traversed and authorable. `GET /api/assets/animator-controllers/{guid}` enumerated `layer.stateMachine.states` and nothing else, so a layer whose states live inside a sub-state machine reported `"states": []` -- indistinguishable from an empty layer -- and every write that resolves a state by name answered `404 State not found` for a state the Animator window plainly shows. Sub-state machines are how any controller past a few dozen states stays readable, so this was the point at which the API stopped describing real projects. Each layer and each machine within it now reports `stateMachines` recursively, with `path`, `position`, `defaultState`, `states`, `anyStateTransitions` -- a property of every machine rather than only the root -- `entryTransitions`, `stateMachineTransitions`, and `behaviours`. Recursion is bounded by `MaxStateMachineDepth`, and a machine at the boundary carries `truncated: true` with no `states` or `stateMachines`, because an empty machine is legal and an empty array would be indistinguishable from one.
- `stateMachinePath` addresses a state anywhere in a layer, and is accepted by `POST`, `PATCH`, and `DELETE .../states`, all three transition endpoints, and all three blend tree endpoints -- the last of which meant a blend tree could previously be authored only on a top-level state. It is an array of state machine names from the layer root rather than a `/`-joined string: Unity does not forbid `/` in a state machine name, so a joined path would need an escaping rule, and an escaping rule is a thing clients get wrong quietly. Omitted or `[]` means the layer's root, so no request that worked changes meaning. Reads report the same array as `path`, so a path read out of a response goes straight back into a request. A path reaching two sibling machines of the same name -- which this API refuses to create but a rename in the Animator window produces -- answers `409` naming the ambiguity rather than choosing.
- `POST` and `DELETE /api/assets/animator-controllers/{guid}/state-machines` create and remove sub-state machines. Removal goes through `AnimatorStateMachine.RemoveStateMachine`, which owns the sub-assets, and the blend trees Unity leaves behind are collected and destroyed as `DELETE .../states` already does. A machine that holds anything answers `409` listing its contents unless `recursive` is `true`: this is a larger operation than deleting a state, and the counts are of the whole subtree rather than the direct children, so a machine holding no states directly but one nested machine holding five is reported as costing five.
- `POST` and `DELETE /api/assets/animator-controllers/{guid}/state-machine-transitions` author `AnimatorTransition`, the type that connects state machines -- entry transitions and the transitions that leave a nested machine. Without them a sub-state machine could be created and never entered. It is a different type from `AnimatorStateTransition` and carries a destination and conditions only, so it is serialized with its own shape: no `hasExitTime`, `duration`, `offset`, or interruption, emitted as absent rather than as zeros that would read as settings. It carries its own `transitionId`, and `transitionId` is the only address, because these transitions have no source state to name.
- `POST .../transitions` accepts `toStateMachine`, so a state can transition into a sub-state machine. Overloading `to` was not an option for the same reason the read now discriminates the destination: a controller may name a state and a state machine alike, and which one a bare name meant would be settled by lookup order.
- Every state in `GET /api/assets/animator-controllers/{guid}` now reports the settings that decide how it plays, and `POST` and `PATCH .../states` write them. The read described a state with four fields -- `name`, `speed`, `isDefault`, `motion` -- and the omissions were not obscure. `writeDefaultValues` decides whether properties a state does not animate are reset to their defaults, differs per state, and is one of the most common reasons a controller misbehaves; a controller built through this API inherited whatever Unity's default happened to be with no way to see or change it. `tag` is what runtime code matches with `AnimatorStateInfo.IsTag`, so a state authored here could not take part in that pattern at all. `iKOnFeet`, `mirror`, and `cycleOffset` are ordinary Inspector fields with ordinary effects. Each of the four parameter overrides -- `speedParameter`, `cycleOffsetParameter`, `mirrorParameter`, `timeParameter` -- is reported beside its own `*Active` flag rather than folded to an empty string when inactive, because Unity stores both and an inactive name is content the asset holds; it also means `speed` can now be read for what it is, since a literal speed beside an active `speedParameter` is not the speed in effect.
- States report `position`, and both write endpoints set it. It is not a property of the state: it lives on the `ChildAnimatorState` struct in the state machine's array, which is what the Animator window reads to lay out the graph, so writing it means assigning the whole array back. Without it a controller authored entirely through the API stacks every state at the origin and the graph is unreadable to the next person who opens it. Unity's field is a `Vector3` and the graph is flat, so `z` is neither reported nor overwritten.
- States report `behaviours`, the type names of the attached `StateMachineBehaviour` instances. A state that runs script on entry was previously indistinguishable from one that does not. It is read-only: attaching one means resolving a script type and instantiating it as a sub-asset of the controller, which is an ownership problem of its own. An entry is `null` where the behaviour's script is missing, which is worth reporting rather than dropping from the array.
- State writes are atomic and validate parameter references. Each override is judged on the pair the request would leave behind -- the value it carries where it carries one, the state's current value otherwise -- rather than on the halves it happens to send, because the two fields are independent in the request and inseparable in the asset. A `*Parameter` naming a parameter the controller does not have is a `400` with neither half written; so is a request that would leave `*Active` true with an empty name, which is an override that drives nothing and which neither half looks wrong enough to cause on its own: activating with no name in the request and none on the state does it, and so does clearing the name of an override that is already on. Turning on an override the state already names is accepted without resending the name, and a name a dormant override still carries is not re-checked, so a patch to an unrelated field is not refused because someone deleted the parameter it points at. Everything is parsed before the first value is written, so a rejected `POST` adds no state and a rejected `PATCH` leaves the other fields unapplied.
- Every transition in `GET /api/assets/animator-controllers/{guid}` now carries a `transitionId`, and `PATCH` and `DELETE .../transitions` take it as the address. Unity permits any number of transitions between the same state pair -- that is how a pair gets several routes, one per condition set -- so `from` plus `to` was never an address, and each verb resolved the ambiguity differently and silently. The id is a `GlobalObjectId` for the transition, which is a sub-asset of the controller with its own `localIdentifierInFile`, and the mechanism `ObjectIdUtils` already uses for GameObjects and Components. Measured on 6000.0.80f1 before it was built on: it resolves after a domain reload, it follows the transition when the `transitions` array is reordered rather than following the position, it is already valid on the transition a `POST` has just created and before `SaveAssets`, and it stops resolving once the transition is deleted -- so a stale id is a `404` rather than a wrong hit. A name pair that matches several transitions now answers `409` listing every candidate with its `transitionId` and its conditions, which are what tell the routes apart; `409` rather than `400`, because the request is well formed and the conflict is in the controller's shape.
- `offset`, `fixedDuration`, `interruptionSource`, `orderedInterruption`, `canTransitionToSelf`, `mute`, and `solo` are now readable and writable on all three transition endpoints. `offset` could already be written and never read back, so a client could set a value and had no way to confirm it. `fixedDuration` matters most: it decides whether `duration` is seconds or a fraction of the source state, so every client setting `duration` was setting a number whose unit it could not determine, and the read now always carries both. Unity's property is `AnimatorStateTransition.hasFixedDuration`, and it is `true` on a newly created transition. An unknown `interruptionSource` answers `400` naming the five accepted values, matching how `type` is handled on `POST .../parameters`. `canTransitionToSelf` is consulted only on AnyState transitions; sent for any other it is stored, as Unity stores it, and named in the response's `unsupported` array rather than passing silently.
- Transition writes are now atomic. Every value is parsed and checked before the first one is written, so a `POST` rejected for a malformed setting adds no transition and a `PATCH` rejected for one bad field leaves the others unapplied, matching what the blend tree endpoints already do.
- `POST`, `PATCH`, and `DELETE /api/assets/animator-controllers/{guid}/blend-trees`. `BlendTree` did not appear anywhere in the package, so after the read landed a client could see a blend tree in full detail and change nothing about it. A tree has no GUID -- it is a sub-asset owned by the controller -- so it is addressed by `layerIndex` and `state`, then a `childPath` of child indices from that state's root. The path is positional, and the documentation says so plainly: Unity gives a `ChildMotion` no identity beyond its index, so inventing one would mean maintaining a mapping the `.controller` file does not store. A nested tree is created only through `addChild`, so there is exactly one way to bring a sub-asset into existence. Every value is resolved against the controller before the first write, so a request that sets several fields and fails on one leaves the tree as it was.

### Fixed

- `GET /api/gameobjects` reports `Quaternion` and `Bounds` properties, where both read as `null`. The endpoint carried its own copy of the property serializer and that copy had no case for either type, so the rotation of every Transform in every project read as nothing -- while the same value read from a ScriptableObject, through the shared serializer, read as `{x, y, z, w}`. One value had two answers depending on which endpoint produced it, and neither page was wrong about its own behaviour, which is what made it a divergence rather than a bug in one place. The copy is gone: the component read now calls `SerializedPropertySerializer` like the asset read, with a flag for the one thing the two genuinely differ on -- a component read resolves a scene object reference and an asset read reports `null`, because an asset cannot hold one. Measured on 6000.0.80f1, `m_LocalRotation` on a Transform turned a quarter turn now reads `{"x":0,"y":0.7071068,"z":0,"w":0.7071068}`, and `m_AABB` on a `SkinnedMeshRenderer` reads `{center, extents}`. Reporting them does not make them writable: `PATCH /api/gameobjects/components` still answers `400` naming the property and its serialized type, which is the behaviour #104 settled. A property that looks like a `Bounds` and still reads `null` is a `Generic` one -- Unity storing a struct with its own children, which a `MeshRenderer` does; it has no `m_AABB` property at all rather than reporting one as `null`.

- Four write paths carried their own copy of the same object-reference field reading -- read `assetType`, resolve it, read `assetGuid` and `assetPath` -- including four copies of the "unknown object reference type" message, so which endpoint a client was talking to could be told from how a malformed reference was refused. One helper now does it for the component write, the ScriptableObject write, the material write and the custom-controller resolver. No response changes: every status and message was measured identical before and after.
- A field of an object reference whose value is not a JSON string is answered `400` naming the field, where it was previously coerced to text and answered `404` for a missing asset. `RequestBodyReader.GetString` returns the raw token when a value is not quoted, so `{"assetGuid": 5}` became the GUID `"5"`, resolved to nothing, and answered `Asset not found … with GUID: 5` — a status and a message about an asset that does not exist, for a request whose fault is a value of the wrong type. Measured on 6000.0.80f1 before the change, on `m_ProbeAnchor`, on an element of `m_Materials`, and on a material's `_MainTex` alike. All six fields a reference carries — `type`, `value`, `scenePath`, `assetGuid`, `assetPath`, `assetType` — now read through one strict reader, so every write that takes a reference gives the same answer: the component write, the ScriptableObject write, the material write, the custom-controller resolver, and query-string `target` parsing, where `{"type": 5, "value": "Main Camera"}` previously reported the type `5` as unknown and `{"value": 5}` searched the hierarchy for an object named `5`. An explicit `null` still reads as absent, because that is what it already meant, and a `404` for a well-formed GUID naming nothing is still a `404`. A client sending a number where a string belongs was never getting the object it asked for; it now finds out which field is wrong. This is the same class as the quoted-number and quoted-boolean cases fixed under #104, with the direction reversed.
- `PATCH /api/assets/materials` selected which property to write by searching the whole `properties` body for `"name"`, the scanner removed from the component and ScriptableObject writes earlier in this release. It survived here because the walk ran the other way round — over the shader's declared properties rather than over the request — so a property name occurring anywhere in the body, including inside another property's value, selected that property for writing. The request now drives the walk, which is also what makes an unaccounted-for key reportable: enumerating the shader can only say what it recognised, never what the client sent and this endpoint did not understand. `Documentation~/api/assets.md` also showed a `guid` field in the response of this endpoint, which it has never sent.
- Rejected `POST /api/assets/scriptableobjects` requests now destroy the unsaved `ScriptableObject` instance created for validation instead of retaining one native Unity object per rejection until unused-object cleanup. Serialized ObjectReference writes now reject unknown and duplicate payload members on both component and ScriptableObject paths, matching the closed value shapes already enforced for Color and Vector values.
- Serialized property writes now validate the complete JSON shape they claim to consume. String properties reject numbers and booleans rather than coercing their raw tokens to text; Color and Vector partial objects require at least one supported member and reject unknown, duplicate, or non-numeric members; and duplicate top-level `properties` keys are rejected instead of applying only the first value. `POST /api/assets/scriptableobjects` uses the same initializer as PATCH and now documents the same all-or-nothing rule: a rejected initial property creates no asset.
- `PATCH /api/gameobjects/components` and `PATCH /api/assets/scriptableobjects` chose which serialized property to write by searching the whole `properties` body for `"name"`, so a key appearing only inside another property's value selected a field the request never named. Every payload these endpoints accept is full of such keys -- the `x` of a vector, the `r` of a colour, the `assetPath` and `assetType` of an object reference -- and the collision needs no exotic field name to reach: any component carrying an object reference field can be hit by a body that mentions that name one level down. Measured on 6000.0.80f1, with `decoy` as the only top-level key in both requests: `{"decoy":{"m_ProbeAnchor":{"type":"hierarchyPath","value":"Directional Light"}}}` answered `200 {"updated":["m_ProbeAnchor"]}` and moved the anchor off `null`, and `{"decoy":{"m_TargetTexture":5}}` answered `400 Object reference property m_TargetTexture must be null or an object.`, failing the whole request -- and discarding every property legitimately in it -- over a field nobody asked to write. Only `ObjectReference` properties could be written this way: the scalar, vector and colour branches read their value through `RequestBodyReader`, which was already top-level strict, so a false match there yielded no value and was skipped in silence. Both write paths now select keys with `RequestBodyReader.HasTopLevelField` and read object reference payloads with a new top-level `GetRawValue`, so the two hand-rolled scanners in `SerializedPropertySerializer` are gone and one implementation decides what a top-level key is. Both documented key forms are unaffected: a top-level field name and a `SerializedProperty.propertyPath` are compared whole, so `m_Sizes.Array.data[0]` still resolves. The behaviour removed is the accidental nested match, which no documented request shape asks for. The shared scanner is stricter about JSON strings than the one it replaces, which the object reference branches now report rather than absorb: a value carrying an invalid escape -- `"assetPath":"C:\Assets\Foo.mat"`, the unescaped Windows path a client writes by hand -- answers `400` naming the property, where reading it leniently used to produce a misleading failure further down.
- `?layerIndex=n` was honoured by the state and transition endpoints and silently ignored by `.../state-machines`, `.../state-machine-transitions`, and the three blend tree endpoints, which acted on layer 0 and answered `201`. The response reported the layer it actually used, so nothing was hidden from a client that read it, but two endpoints disagreed about what addresses a layer. The cause was four private implementations of one read -- one with the query fallback, three without, and two different wordings for the out-of-range error. There is now one, on `AnimatorStateMachineAddress` beside the `stateMachinePath` resolution it belongs with, and `layerIndex` as a query parameter is documented for the first time. A query value that is present and not an integer answers `400` rather than defaulting to the base layer. `DELETE .../states` gains the layer count in its out-of-range message, which the shared wording carries and its own inline copy did not.
- A `toStateMachine` that does not resolve said `stateMachinePath does not resolve`. The two fields carry paths resolved from different roots -- `stateMachinePath` from the layer root, `toStateMachine` from the machine that path addressed -- so a request with a correct source and a wrong destination was told to check the one field that was right, and the path echoed in the message was the other field's. Both messages now name the field they read, and the field is a required argument rather than a defaulted one so that the next call site cannot inherit the wrong name silently.

- Consecutive AnimatorController writes accumulated into a single undo entry, so one Ctrl+Z took back all of them. This is the same defect as the scene-write one fixed earlier in this release, at a site the earlier fix did not reach, and it was missed for a specific reason: the animation handlers register no undo of their own, because the `UnityEditor.Animations` editing APIs register theirs. "We add no undo" reads as "we need no undo code" -- but an undo group is not a registration. Unity's registration lands in whichever group is current, and nothing advances the group between two HTTP-triggered main-thread callbacks; Unity advances it after a human interaction with the Editor, which is exactly what does not happen when the Editor is driven over HTTP. Measured on 6000.0.80f1: four consecutive `POST /api/assets/animator-controllers/{guid}/states` calls were all removed by a single Ctrl+Z, and so were two consecutive `POST .../state-machines` calls. Every controller structure write -- parameters, layers, states, transitions, blend trees, state machines, and state machine transitions -- now opens its own group through the shared `UndoGroups.Begin` before it mutates anything and collapses to it afterwards, so one request is one undo entry and the entry carries the operation's name into Edit > Undo History. The `POST .../layers` rollback path collapses to the same group, so a layer that is created and then taken back for a rejected setting does not leave an entry of its own. AnimationClip writes are unchanged and remain outside the undo stack by the decision recorded in the animation API reference: they register nothing, so a group would have nothing to hold.

- `ObjectRefUtils.ResolveType` answered `500` for an unknown type name whenever the domain held an assembly whose types could not all be loaded. Its fallback scan called `Assembly.GetTypes()` on every loaded assembly with no guard, and that call throws `ReflectionTypeLoadException` rather than returning the types that did load, so one such assembly took the whole lookup with it. Measured on 6000.0.80f1: `POST /api/assets/animation-clips/{guid}/curves` with an unknown `type` answered `400 Unknown type: NoSuchType` before, and `500` carrying `Type 'Unfinished' is not finished` after a dynamic assembly holding an uncreated `TypeBuilder` entered the domain. Unity's own expression evaluator produces one -- the failing type is named `<InteractiveExpressionClass>` -- which is why this came and went during a session with nothing in the project to explain it, and why it kept surfacing as unrelated test failures on other branches. The scan now falls back to `ReflectionTypeLoadException.Types` and skips the nulls, which is the guard `EditorMenuItemsHandler` and `UnionAirRouteRegistry` already applied to the same call; the assembly still contributes the types that loaded rather than being skipped whole. The resolver is shared, so the same `500` was reachable from component writes, ScriptableObject writes, Play mode UI lookup, and object reference resolution. Names that already resolved are unaffected: Mono appends dynamic assemblies last, so anything matching earlier never reached the throw.
- Consecutive writes through the API accumulated into a single undo entry, so one Ctrl+Z took back all of them. Every scene write path named its undo group with `Undo.SetCurrentGroupName` but never opened one -- that call renames the current group, and `Undo.IncrementCurrentGroup` appeared nowhere in the package. `Undo.GetCurrentGroup` therefore returned the group the previous request was already in, and `Undo.CollapseUndoOperations` merged that request into this one. A hand edit was never affected, because Unity advances the group after a human interaction with the Editor; nothing advances it between two HTTP-triggered main-thread callbacks, which is exactly the case UnionAir is driven in. Measured: adding a component to one object and then to another, then a single Ctrl+Z, removed both. Each write path now opens its own group through a shared `UndoGroups.Begin`, so one request is one undo entry, and a batch request remains the single entry it was always meant to be.
- `DELETE /api/assets/animation-clips/{guid}/curves` removed nothing and reported that it had. It removed float curves with `AnimationClip.SetCurve(path, type, property, null)`, which does not remove a binding -- only the `AnimationUtility` form does -- and it appended every requested binding to `removed` unconditionally, so the response described the request rather than the result. A client deleting a curve received `{"removed":["localPosition.y"],"errors":[]}` and a clip that still held every curve it started with. Object reference curves were already removed correctly and are now covered by the same reporting.
- The same endpoint now addresses bindings by the serialized property name that `GET` returns. Adding and removing go through different Unity APIs, so the name a client writes is not always the name the clip stores: `POST .../curves` writes through `AnimationClip.SetCurve`, which expands a Transform vector property into all of its components -- a curve on `localPosition.y` is stored as `m_LocalPosition.x`, `.y`, and `.z`, with the untouched components pinned to the property's default value -- while removal goes through `AnimationUtility.SetEditorCurve`, which addresses exactly one binding. The expansion belongs to `SetCurve` rather than to the shorthand; the serialized name expands the same way. A `property` that matches nothing is reported in `errors` together with the names that are bound at that path and type, so the correct one can be read off the failure, and `removed` now lists only bindings that were present before the call and absent after it. A request where nothing was removed and at least one binding failed answers `400` rather than `200`, matching how the add endpoint already reports a wholly failed request.
- `POST /api/assets/animation-clips/{guid}/curves` described the request rather than the bindings it wrote, which is the defect `DELETE .../curves` was fixed for earlier in this release, on the other half of the same endpoint. It appended each entry's `property` to `added` and never looked at the clip, so the response was accurate only when the name happened to survive the write unchanged. Measured on 6000.0.80f1: writing `localPosition.y` answered `{"added":["localPosition.y"],"errors":[]}` against a clip that held `m_LocalPosition.x`, `.y`, and `.z` -- one name for three bindings, none of them the name reported, and the two the caller did not ask for pinned to `0` for the clip's whole length. Sampled onto a child authored at `(11, 22, 33)`, the clip drove it to `(0, 0, 0)` at `t=0` and `(0, 5, 0)` at `t=1`. The name was also the one thing a caller could not reuse: handing it back to `DELETE .../curves` answered `400`, because removal addresses the serialized name. Each entry's result is now measured by performing that one write on a throwaway clip and reading the bindings back -- `SetCurve` is the only thing that knows what a property name resolves to, and the mapping is not derivable from the name (`localEulerAngles.y` becomes `localEulerAnglesRaw.x/.y/.z`, which `AnimationUtility.GetAnimatableBindings` does not report for `Transform` in any spelling). Every produced binding is then confirmed against the saved clip, and one that is not there is an error rather than a silent success. A throwaway clip rather than a before-and-after diff of the real one, because a request that replaces an existing curve creates no binding and a diff would report that nothing was written.
- The property name is still not checked against what the type can animate, and the documentation now says so rather than leaving it to be discovered. `SetCurve` accepts any name, so `bogusProperty.y` becomes a binding that animates nothing. Validating against `AnimationUtility.GetAnimatableBindings` was considered and rejected on measurement: that set does not contain `localEulerAnglesRaw`, and it is a property of the object rather than of the type -- a bare `SkinnedMeshRenderer` on a scratch GameObject reports 14 bindings, while the same type carrying a character's meshes reports 819 to 830 and only then includes the `blendShape.*` and `material.*` names that real clips animate. A check against the type's set would reject working euler, blend shape, and material curves, and the set that would make it correct belongs to the object at `relativePath`, which a `POST .../curves` body does not name.
- `POST` and `DELETE /api/assets/animation-clips/{guid}/curves` rejected a fully qualified type name for everything except five UI types. `type` accepted `Transform` but answered `Unknown type: UnityEngine.Transform`, while `UnityEngine.UI.Image` worked -- because the five UI names were written into a hand-maintained switch by hand and the fallback beneath it prepended `UnityEngine.` to whatever it was given, turning an already-qualified name into `UnityEngine.UnityEngine.Transform`. The documentation offered `UnityEngine.UI.Image` as its example of the form, so the spelling that looked recommended was the one that failed. These endpoints now share `ObjectRefUtils.ResolveType`, which every other endpoint already used, with `UnityEngine.Object` required as the base type: the shared resolver falls back to matching on simple name across every loaded assembly, and without that requirement `Image`, `Slider`, `Button`, and `Text` resolve to `UnityEngine.UIElements` and `System.Net.Mime` types instead of the `UnityEngine.UI` ones. Every spelling the switch accepted still resolves to the same type, and a type that is not a `UnityEngine.Object` is now reported as `Unknown type` rather than accepted.
- `ObjectRefUtils.ResolveType` threw on an empty type name instead of answering `null`, because `Assembly.GetType` rejects an empty string. No caller could reach it, since each rejected an empty name first; the animation curve endpoints default `type` rather than requiring it, so `"type": ""` reached the resolver and would have answered `500` with the exception text in the body. It answers `Unknown type` like any other name that resolves to nothing.
- `DELETE /api/assets/animator-controllers/{guid}/states` left blend trees in the `.controller` file. Measured on 6000.0.80f1 against the file rather than the API's own read: `RemoveState` destroys the state's own motion tree but not the trees nested inside it, so removing a state whose tree had one nested child left a `BlendTree` with no state and no parent referring to it. A flat tree is cleaned up correctly, which is why this only appears once a tree is nested and why a one-level test would have reported success. The subtree is now collected while it is still reachable and whatever survives the removal is destroyed, reported as `destroyedBlendTrees`. The same applies when a blend tree child is deleted, where Unity leaves the entire detached subtree behind; clearing a state's motion needs no such handling, because there Unity does destroy every descendant.

- `DELETE /api/assets/animator-controllers/{guid}/transitions` left the removed transition in the `.controller` file. It rewrote the state's `transitions` array without the entry, which detaches the transition but does not destroy it: an `AnimatorStateTransition` is a sub-asset of the controller, and measured on 6000.0.80f1 the array assignment left two transition sub-assets where one was still referenced, while `AnimatorState.RemoveTransition` left one. Every delete since the endpoint shipped therefore grew the asset by an orphan. Removal now goes through `RemoveTransition` and `RemoveAnyStateTransition`, which own the sub-asset's lifetime.
- Layer writes now validate every value before it reaches Unity, because the editing API answers an illegal one by damaging the controller rather than by refusing it. Measured on 6000.0.80f1: `RemoveLayer(0)` does not refuse and leaves a single-layer controller with zero layers; a `syncedLayerIndex` pointing at its own layer removed a layer silently, three becoming two with no error; and one index past the last layer crashed the Editor outright. Deleting layer 0, deleting a layer another layer syncs to, and an out-of-range or self-referential `syncedLayerIndex` each answer `400` naming the reason. Deleting a layer that is itself synced clears the sync first: `RemoveLayer` does not destroy the state machine of a synced layer, which otherwise left the `.controller` file holding an `AnimatorStateMachine` that no layer referred to.

### Documentation

- `POST /api/editor/menu-item` documents that `executed: true` reports the dispatch and not the effect. It is `EditorApplication.ExecuteMenuItem()`'s own return: the item was found, was enabled, and was invoked. A menu item whose command reads the focused `EditorWindow` has no window to read over REST, so it is dispatched and does nothing, and the page said nothing about it — `404` for "not found, is disabled, or could not be executed" reads as though a `200` means the command ran. Measured on 6000.0.80f1 with the selection confirmed first: `Edit/Duplicate` copies neither a scene object nor an asset, `Edit/Delete` leaves the selected GameObject in place, `Edit/Select All` leaves the selection alone, and `Assets/Create/Folder` creates nothing — each answering `200 {"executed": true}`. `Edit/Undo` is the contrast and does act, so the dividing line is whether the command needs a focused window rather than which menu it sits under. No second field is added, because UnionAir cannot know what an arbitrary menu item was supposed to do; the page now says to verify the effect with a read, and to prefer a typed endpoint where one exists.

- The ScriptableObject reference no longer claims that `GET /api/assets/scriptableobjects/{guid}` does not serialize arrays. It has since the read gained array support, and the reference said otherwise from the same commit that added it -- the property table sent readers to `GET /api/gameobjects` for "array-valued component properties", and the response sample showed an array field as `null`. Measured on 6000.0.80f1, the read of a `UniversalRendererData` asset returns `"m_RendererFeatureMap": [1871080365]` and its object reference array as `assetGuid`/`assetPath`/`assetType` objects. A client that trusted the table had no reason to look at a field it was told would be empty.
- The examples in `[UnionAirEndpoint]` are checked rather than trusted. They are served to clients through `GET /api/help?detail=full` and nothing held them to anything, which is how the AnimatorController read's example survived two breaking changes to its own response. Every `RequestExample` is now validated against the field list its own endpoint declares, using the same reader the handler will use, and every `ResponseExample` must parse. The AnimatorController read -- the largest response in the package and the one that drifted -- is additionally compared field by field against a real read of a controller built to that shape. Demonstrated by reverting the example alone to its pre-#67 form: the comparison fails and names `to`.
- The `POST .../curves` reference explains the expansion where it happens. It was written up under `DELETE .../curves`, because that is where a client discovers it -- by having a name rejected -- but the section for the endpoint that performs the expansion said only that `property` is a "serialized property path (e.g. `localPosition.y`)". A reader of the endpoint they were calling got no hint that one entry can produce three bindings and pin two axes. Both language versions now carry it, along with the four `Transform` groups the rewriting actually covers, the response fields, and the statement that the name is not validated. The groups were written up as "position, scale, and euler angles", which left out `localRotation` -- the one that stores four components rather than three, because the stored rotation is a quaternion -- and read as a general translation from scripting names to serialized ones, which it is not: measured on 6000.0.80f1, `Light.intensity` is stored as `intensity` rather than `m_Intensity`, and `Transform.position.y` as `position.y`. Both animate nothing. Two silent failure modes of the group write are now written down as well, both measured rather than reasoned about. A component suffix that names nothing in the group still selects the group, and the keys then have nowhere to land: `m_LocalPosition` and `m_LocalPosition.w` each create `m_LocalPosition.x/.y/.z` carrying no keys at all, and the response reports three bindings and no error. And rotation written as a single `localRotation.y` entry fills the quaternion's `w` with `0`, which normalizes to a half turn whatever `y` holds -- a curve authored to reach 90 degrees reaches 180. Four entries covering `m_LocalRotation.x/.y/.z/.w` reach 90, and so does one `localEulerAngles.y` entry, because there the unwritten components default to the identity. The reference also states that the pinning of the axes a caller did not ask for is not caused by the expansion: Unity combines a Transform's component curves into one Vector3 or Quaternion curve and fills a curveless component with its default, so a clip holding `m_LocalPosition.y` alone drives `x` and `z` to `0` just the same. The expansion makes that visible in the asset rather than causing it.
- The animation API reference now states which animation writes the Editor can undo. AnimatorController structure writes are undoable and always were -- the `UnityEditor.Animations` editing APIs register their own undo, so UnionAir adds none and a request that adds a state is taken back by one Ctrl+Z. AnimationClip curve writes are not, by choice: they are saved to disk before the response is sent, so a `200` means the file already changed and recovery belongs to version control; registering undo would revert the asset in memory while the file kept the written content until some later unrelated save. Asset creation is not undoable in Unity itself. Measured on 6000.0.80f1 rather than inferred, including the case that an earlier draft of #64 had backwards.

## [0.5.0] - 2026-08-07

### Upgrade Notes

- Custom controllers receive `UnionAirRequest` and `UnionAirResponse` instead of `System.Net.HttpListenerRequest` and `HttpListenerResponse`. A controller that only passes `ctx.Request` and `ctx.Response` to `RequestBodyReader` and `RestResponse` compiles unchanged. A controller that declares its own helper typed against the framework types must change those parameter types. The `HttpListenerResponse` overloads of `RestResponse.Send`, `SendBinary`, `SendError`, and `SendNotFound` are removed rather than retained as obsolete.

### Changed

- The handler-facing request and response are now UnionAir's own abstract types, implemented by adapters over `HttpListener`. Both are `abstract class` with an `internal` constructor rather than interfaces, so members can be added later without breaking anyone, while `InternalsVisibleTo` still lets the test assemblies supply substitutes. The transport is no longer part of the contract, and a handler can no longer reach a stream that nothing else can observe: the request body stream is internal to `RequestBodyReader`, which is what makes a single cached read the rule rather than a convention.
- `RestRouter.Handle` now takes a request and a response instead of an `HttpListenerContext`, and the server wraps each dequeued context once before dispatching it.

### Added

- The Request Log gained a **Details** action per row, opening a window that shows the request line, headers, and body above the response status, content type, duration, and body. Pressing it for another entry updates the open window rather than adding one. Bodies can be copied or saved, and the request can be copied as an executable `curl` command with the active Base URL and the `Content-Type` the API requires already filled in; the command is not offered for an entry whose request body was truncated. It emits `curl.exe` rather than `curl`, because in Windows PowerShell 5.1 the bare name is an alias for `Invoke-WebRequest`. The arrow beside the button chooses the shell to quote for -- bash, PowerShell 7, or Windows PowerShell 5.1 -- and the choice is remembered in `EditorPrefs`, next to the window's tab and foldout state; which shell someone pastes into belongs to their machine rather than to the project, so it is deliberately not part of `.unionair/settings.json`. No single form works everywhere: bash and PowerShell 7 both take a single-quoted argument verbatim but write a literal single quote differently, while Windows PowerShell 5.1 cannot be served by ordinary argument syntax at all -- it passes a value containing `\"` to the process unquoted, so the body splits at its first space, and it strips delimiter quotes written by hand. Its command therefore uses the `--%` stop-parsing token, after which Windows' own command-line rules apply and a double quote reached through `n` backslashes is written with `2n+1` of them. A binary response is described by content type and size rather than rendered, and an oversized body is displayed truncated with the whole content still available through copy and save. A window restored after a domain reload reports that the record is gone instead of rendering stale content. What is displayed is produced by a formatter kept apart from the windows, so the layout can be rearranged without changing any of it.
- Every HTTP exchange is now recorded in a bounded in-memory store: request line, headers, and body; response status, content type, body, and duration. The entry is opened when the request is dequeued and closed by the response itself, so a deferred response -- an artifact download, a replayed input sequence -- reports the duration through to its actual close rather than to the handler's return. Capture happens through the response's own output stream rather than by hooking `RestResponse`, so a custom handler that writes to the stream directly is recorded like any other. The store retains 200 exchanges, caps request bodies at 64 KB and response bodies at 256 KB, and records truncation instead of presenting a partial body as whole. Binary responses are measured rather than buffered, since screenshots and artifact downloads run to megabytes. Entries are held for the current Editor session and are lost on a domain reload.
- `RestRouter` gained tests. The framework request and response types are sealed with no public constructor, so nothing that accepted them could be exercised without a live server, and the suite had been shaped around that limitation since the beginning: handlers were tested through extracted pure helpers, and `RequestBodyReaderTests` documented that its request overloads were unreachable. Origin rejection, the `OPTIONS` answer, the not-found response, and the method-not-allowed response are now covered directly, as are the request overloads of `RequestBodyReader` including the single-read guarantee. The gates that depend on Editor state -- the Play Mode opt-in, the test-run rejection, and the disabled-category response -- still require that state to be arranged and remain uncovered.

Schema-backed EditorWindow controls update an in-memory working document and atomically save the complete UTF-8-without-BOM v1 file after every change; failed writes remain dirty and retry automatically. Built-in categories, custom handlers, and Play Mode scene changes use one authoritative set of UI controls, with a convenience action that disables every sensitive API while preserving server settings. The file remains visible to Git while runtime discovery files stay ignored.

It previously dispatched the run first and wrote the record afterwards, so a failed write escaped as an unhandled exception with a real run already in flight and the armed profiling session orphaned. Attaching a profiling session, which writes to disk the same way, moved ahead of the dispatch for the same reason.
- The run id in `POST /api/test-runs` is now issued by UnionAir rather than taken from the Unity Test Framework. The framework returns its own id only once the run has been dispatched, which is exactly what made recording the run first impossible; its id is kept privately as the handle cancellation needs. The value is still an opaque GUID string and no response changed shape, so clients see no difference. `DELETE /api/test-runs/{id}` gains one `409` case, for a run the framework accepted without naming.
- A test-run activity left open with no live UnionAir record behind it is now released at initialization, with a Console warning, using the shared predicate the other three services adopted. Nothing else would have closed it: `SessionState` outlives every domain reload, the Test Framework poll that would otherwise recover it does nothing when the framework cannot be inspected, and the test-run gate is evaluated before the category check, so a stuck one refused nearly the whole API for the rest of the Editor session. The check is scoped to activities UnionAir owns, because a run started from the Test Runner window is adopted with no record at all and would otherwise be released while still running.
- The matching crash net now tests that the open activity is the one this service opened, not merely that some activity is open. An external run adopted after a UnionAir record was lost used to protect that record indefinitely, leaving a run nothing could finish.
- Test-run records are written through the shared store that retries once and reports failure, rather than one that throws. A failed write now schedules its own retry, so the last-chance flush before a domain reload still runs — without it, a run that finished but could not be stored came back as `aborted` after the reload.

- Added build target switching. `POST /api/build/target` switches the active target and returns `202` with the id to poll; `GET /api/build/target` and `GET /api/build/target/{id}` read the in-flight switch and the retained records. It is modelled as a lifecycle operation rather than a settings write, because it reimports every asset for the new platform, recompiles, and ends in a domain reload.
- The switch record survives that reload. Unity reports nothing across it, so UnionAir resolves the record on the far side by comparing the active target against the one requested — the only piece of evidence that outlives the reload.
- A missing platform module is reported as `409` with `code: "platform_module_not_installed"` and the targets that are installed, rather than as a generic switch failure. The fix is installing the module from the Unity Hub, which nothing about a failure message would suggest.
- Requesting the target that is already active returns `200` with `state: "unchanged"` and creates no record.
- `POST /api/build/target` returns `500` without starting anything when the switch record cannot be written. The record is the only thing that survives the domain reload the switch causes, so a switch begun without one could never report its outcome and would leave an activity nothing closes.
- A queued switch resolves to `failed` rather than staying queued forever when an unrelated domain reload discards its deferred start.
- The stale-activity check for a target switch tested the record's active state with the wrong polarity, so a terminal record could be accepted as the owner of a still-set flag. It now uses the shared, tested predicate.
- A queued or running target switch now makes `GET /api/editor/status` report `settled: false`. It previously reported `settled: true` alongside an `activeActivity` naming `buildTargetSwitch`.

- Added persistent build settings changes. `PATCH /api/build/settings` changes the scripting backend, API compatibility level, stripping level, IL2CPP compiler configuration, define symbols, and build flags for a named build target; `POST /api/build/scenes` replaces the build scene list. This is what makes the original motivation of the umbrella issue achievable — evaluating the effect of a settings change on compilation.
- Both endpoints state persistence explicitly per change. `project` persistence writes `ProjectSettings/ProjectSettings.asset` or `ProjectSettings/EditorBuildSettings.asset`, which appear as Git diffs and reach everyone working on the project; `user` persistence writes the per-user `Library/EditorUserBuildSettings.asset`. Presenting build flags and scripting settings as one kind of "setting" would have been the misleading part.
- Every value is validated before anything is written, so an invalid request changes nothing. Past that point a failed change is reported rather than rolled back — undoing earlier writes could fail too and leave a third state — so each change carries `applied`, `unchanged`, or `failed`, the status is `207` when any failed, and the response includes the resulting settings.
- Define symbols are validated as identifiers. Unity stores whatever it is given and fails later, at compile time, with an error that never mentions the setting.
- A change that triggers compilation reports `compilationExpected` and returns before the domain reload; the cycle is then observable through `GET /api/compile`.
- A field that is present but is not the type it should be returns `400` naming the field, rather than being dropped silently. `"development": "true"` previously applied nothing and reported no outcome for it, contradicting both the pre-write validation and the acknowledgement rule. A scene entry's `enabled` is checked the same way, where defaulting to `true` would have shipped a scene the caller asked to exclude.

- Added player builds to the Build category. `POST /api/builds` requests a build for the active target and returns `202` with the id to poll; `GET /api/builds`, `GET /api/builds/{id}`, and `DELETE /api/builds/{id}` read, enumerate, and reclaim them. A build is the only check that covers what compilation and EditMode tests do not: player-target assemblies, stripping, scripting backend, and platform-specific define symbols.
- A build occupies the Unity main thread, so **UnionAir answers no request while one runs** — measured at roughly 72 seconds for a Windows player, 22–34 seconds warm. The record is persisted and the `202` sent before the build starts, and the response says so, so a client can set its timeouts. Live progress and cancellation are not offered because neither is achievable in process.
- Build output and its `report.json` are written to `Builds/UnionAir/{id}/` under the project root, with a generated `.gitignore` containing `*`. `Library/` is deliberately not used: Unity regenerates it, which would either destroy a hundred-megabyte artifact silently or orphan it from its record. Retention trims oldest-first under a 3-directory, 2 GiB cap set independently of the profiling quota, and `GET /api/builds` reports total usage so disk consumption stays visible despite the git exclusion.
- The completed `BuildReport` is snapshotted into a durable DTO the moment `BuildPipeline.BuildPlayer` returns, because the report is a Unity object a domain reload discards. Records reach `queued`, `running`, `completed`, `failed`, or `aborted`, are written atomically, and survive a domain reload or an Editor crash.
- `POST /api/builds` rejects a request with `409` when any loaded scene has unsaved changes. `BuildPipeline.BuildPlayer` reads scenes from disk and does not prompt from script, so an unsaved scene would be silently excluded and the build would report success for content that does not match the Editor. Scenes are never saved implicitly.
- A replayed `requestId` returns `409` with the existing record rather than starting a second build. This matters more than for compilation: the connection drops for the whole build, so losing the `202` is a realistic outcome.
- `GET /api/editor/status` now reports `buildState` and `buildId`, and a queued or running build makes `settled` false.
- `POST /api/builds` returns `500` without starting anything when the build record cannot be written, and `DELETE /api/builds/{id}` returns `409` for a build that is still queued or running. Deleting the record a queued build waits on would leave nothing to release its activity, and the project would report itself busy for the rest of the Editor session.
- `POST /api/builds` rejects an option that is present but is not a JSON boolean, instead of silently falling back to the project default and producing a build the caller did not ask for.
- A build always reaches a terminal state and always releases its activity. The tail of the run was outside the exception handler, so anything thrown there escaped without committing the record — and unlike a compilation or a target switch, a build causes no domain reload for the recovery pass to run in.
- A queued build now resolves rather than waiting forever when its deferred start never runs — a domain reload between the `202` and the start discards the callback with the domain. `CompileService` already guarded its queued window this way; the build service had no watchdog.

- Added a single coordination point for mutually exclusive Editor activities — compilation, test runs, Play mode, asset updating, builds, and build target switches. UnionAir previously tracked these with two independent `SessionState` gates plus ad-hoc checks inside individual handlers, which made a third one untestable. Declared activities keep durable identity across domain reloads; Play mode and asset updating are observed from `EditorApplication` rather than mirrored.
- `GET /api/editor/status` now reports `activeActivity` with the activity name, its source, and the id that owns it. When several activities are running it reports the most exclusive one, so a client is told to wait for the build rather than for the compilation the build is running.
- A `409` caused by the Editor being busy now carries an `activeActivity` object. The shipped `activeTestRun` and `activeCompile` objects are unchanged and still present.
- Endpoints and categories now declare `blockedDuring` in `GET /api/help` — the complete list of activities during which the endpoint is rejected, including the ones enforced by `playModePolicy` and `testRunPolicy`, so a client reads one array instead of reconstructing it from three fields.
- Added `Documentation~/api/activities.md` describing the activity vocabulary, the rejection shape, and why enforcement of Play mode and test runs stays separate from the generic gate.
- An operation UnionAir starts now persists its record **before** opening its activity, and answers `500` without starting anything when that write fails. `InputReplayService` already worked this way; `CompileService` did not, and the new build endpoints had copied the wrong precedent. The write is retried once immediately, because a scanner or indexer briefly holding the destination is the common transient cause and clears by itself, while a full disk does not. Activity UnionAir merely adopts — a compilation an IDE triggered — cannot be refused and stays best-effort.
- The "is this activity debris" predicate is one shared, tested function rather than a copy per service. The three hand-written copies had already drifted: one omitted the terminal-record test and one inverted it, so a terminal record could be accepted as the owner of a still-set flag and the release would never happen.
- Activity coordination now recovers in both directions. The existing crash net finds a record claiming to run with no activity open; the new mirror check finds an activity open with no live record and releases it with a Console warning. Nothing else could close it — `SessionState` outlives every domain reload — so the Editor would otherwise report itself busy, and reject every endpoint declaring a conflict, for the rest of the session.

- Added a disabled-by-default **Build** category with read-only build configuration endpoints. `GET /api/build/settings` reports the active build target, the build scene list with the build index Unity actually assigns each entry, the scripting backend, API compatibility level, stripping level, and define symbols for a named build target, plus the development and debugging flags a build would use. `GET /api/build/targets` lists the build targets this Editor defines and whether each platform module is installed — which is a property of the Editor rather than the project, so nothing in the project directory reports it.
- Added the `executableOutput` endpoint risk for endpoints that produce runnable output rather than project files, and reported it as the risk of the Build category. No existing risk flag expressed it.
- Added `GET /api/compile/records` to enumerate retained terminal compilation summaries in deterministic newest-first order, with bounded offset/limit pagination and target, source, and state filters.

## [0.3.0] - 2026-08-01

### Added

- `POST /api/editor/play` now accepts an optional `inputs` list that schedules frame-accurate input, replayed from the first Play mode frame. `frame` means the frame the game observes the input on — the frame where `wasPressedThisFrame` is true inside the game's `Update()` — not the frame an event was queued. Events sharing a frame are merged into a single state snapshot per virtual device, so chords reach the game as simultaneous presses. Without `inputs` the endpoint is unchanged; with it the response is `202` and carries the replay id. Requires the `com.unity.inputsystem` package.
- Added `GET /api/playmode/input/result` in the always-enabled Read category, reporting the current or most recently finished replay. Each event carries the frame it was actually observed on rather than the frame requested, so a client can prove the schedule held instead of assuming it. The endpoint doubles as the completion signal: it is how a caller knows when inspecting the game's state is meaningful. A failed event is recorded and the replay continues, so `failedCount` matters even when `state` is `completed`.
- The whole `inputs` list is validated before Play mode is entered, and a single invalid entry returns `400` naming its index without arming a replay or leaving Edit mode. Entering Play mode causes a domain reload and the response is sent before the replay runs, so a problem found later could not be reported at all. There is no cap on list length or frame range; `POST /api/editor/stop` ends a runaway replay.
- `POST /api/playmode/input/{perform,set,pointer}` now return `409` while a replay is active. They call `InputSystem.Update()` synchronously, which would flush the replay's queued events outside the player loop and destroy its frame timing.

Diagnostics are structured with `severity`, `code`, project-relative `file`, `line`, and `column` instead of requiring callers to parse Console text.

The record is persisted and the response sent before any compilation work starts, because refreshing and compiling block the Editor and can end in a domain reload that drops the connection. An optional caller-supplied `requestId` makes a lost response recoverable, and `409` responses carry `activeCompile` or `existingCompile` so a caller knows to poll rather than retry.

- Compile records distinguish `succeeded` from `upToDate`, so a caller can tell "compiled with no errors" from "Unity reported zero compiled assemblies." Neither result promises whether a domain reload follows; removal-only cycles can report `upToDate` and still reload. Cancelled and interrupted cycles resolve to `aborted` rather than remaining active.

The cursor is applied before the `type` and `search` filters, so `truncated` reports lost entries rather than filtered ones.

Initialization no longer prunes persisted baselines from an incomplete early scene list, readiness and file-read retries are bounded, and a failed scene-open/save baseline records one actionable warning instead of silently leaving the scene untracked.
- `DELETE /api/assets/{guid}` now returns a structured `409 Conflict` before deleting a loaded scene or a folder containing loaded scenes, preventing the open scene from losing its backing asset.
- Request-body fields are now read correctly from pretty-printed JSON. The body reader skipped only spaces and tabs after a field's colon, so a value placed on the following line was reported as absent — every endpoint using `GetString`, `GetInt`, `GetFloat`, or `GetBool` was affected.
- Reading a JSON array is now anchored to its own field. A non-array value such as `"operations": null` previously made the reader scan forward and adopt an unrelated later array in the same body, silently processing the wrong elements.
- `POST /api/playmode/input/set` now reads `value` through the shared array reader, which no longer matches a `"value"` key nested inside another object or inside a string literal. A Vector2 `value` must now hold exactly two numbers; a longer array was previously accepted and silently truncated to its first two elements.
- Screen-coordinate endpoints now reject a `position` or `normalizedPosition` that is present but not an object, such as `"position": null`. The value previously read as an absent field, which mattered most for `POST /api/playmode/input/pointer` with mode `release`, where an absent coordinate means "use the current position" — a malformed coordinate silently released somewhere else instead of failing.

- Prevented mixed player or custom compilation cycles from being classified as Editor cycles and replacing `latest`, and re-evaluated retained records with the conservative target rules at startup.
- Prevented caller-supplied compile ids such as Windows device names from being accepted when their per-id record cannot be persisted safely.
- Made Console NDJSON downloads include the same-session rotated predecessor instead of making entries inaccessible as soon as the active file crossed the rotation threshold.
- Kept compile record retention going past a record that cannot be deleted, instead of abandoning the remaining trim and letting the retained set grow without bound.
- Backed off log rotation by size after a failed attempt. A rotation blocked by a concurrent NDJSON download previously left the file over the threshold, so every following Console message closed, retried, and reopened the log writer.
- Stopped rebuilding `latest` from retained records on every domain reload once a scan has already found no eligible completed Editor cycle. Skipping the rescan no longer keeps a stale non-Editor record as `latest`, the removal of that record is retried on every reload until it succeeds, and a scan interrupted by an I/O error is retried instead of being treated as proof that nothing eligible exists.
- Moved persistence of log rotation state onto the Editor update loop so that `GET /api/editor/logs.ndjson` no longer writes session state as a side effect of a read.
- Stopped a multi-file artifact transfer when a stream ends before its announced length, rather than appending the next file onto a partial record.
- Prevented domain reloads from orphaning an `HttpListener` by retaining listener ownership until bounded thread and queued-response cleanup completes.
- Added up to five bounded retries for transient address-in-use failures during automatic startup, without publishing intermediate failures to the Console or logs API.
- Added up to three delayed recovery attempts for unexpected listener thread exits, with cleanup completed before the bounded lifecycle trace is dumped and concise errors kept separate from the once-per-domain trace.
- Prevented failed profiling restoration from leaving undeletable active sessions or owned Profiler settings behind.
- Moved profiling artifact downloads off the Unity Editor update loop and cached finalized session statistics instead of reparsing NDJSON on every status request.
- Made active NDJSON downloads share-safe and length-bounded, handled background-transfer queue failures, and limited sessions to 64 metrics to bound memory use.
- Active object searches now select the Unity 6000.4 no-sort-parameter API while retaining the established overload on earlier Unity 6 releases, removing new obsolete warnings without raising the minimum supported Unity version.
- Test Runner request filters now use the shared top-level JSON parser, avoiding false matches for filter names embedded inside string values.
- Test-run progress metadata is now persisted at a bounded interval and at lifecycle boundaries instead of performing an atomic disk write for every test callback.
- Unity Test Framework active-run inspection now uses a cached delegate at a bounded polling interval, reports compatibility failures, and safely rejects new runs when concurrency cannot be verified.
- Test execution and discovery now share a correctly created, domain-scoped `TestRunnerApi` ScriptableObject instead of constructing an undisposed instance for each request.
- Test-run source identifiers, public run IDs, nullable JSON string formatting, and the EditorWindow's core category order now each use a single definition to prevent silent drift between API responses and UI rendering.
- Test-run gates now reconcile in both directions after a grace period when Unity Test Framework is positively observed as idle, preventing missed completion callbacks from leaving external or UnionAir runs locked until an Editor restart.
- Latest NUnit XML and metadata now use a recoverable transaction and SHA-256 integrity check, preventing a crash between file replacements from serving one run's XML under another run ID.
- `POST /api/playmode/input/perform` now resolves Keyboard bindings through the virtual device's actual `KeyControl`, preventing top-row numeric paths such as `<Keyboard>/1` from being parsed as numeric `Key` enum values and pressing unrelated keys.

### Added

- `PATCH /api/assets/texture-importer/{guid}` — updates texture import settings (`textureType`, `spriteMode`, `pixelsPerUnit`) and calls `SaveAndReimport()`. Required for converting Texture2D assets to Sprite type before using them in object reference curves.

For Sprite-mode textures, the Sprite sub-asset is loaded automatically via `AssetDatabase.LoadAssetAtPath<Sprite>` to avoid type mismatches with `m_Sprite`.
- `DELETE /api/assets/animation-clips/{guid}/curves` — removes curves by binding. Automatically selects `AnimationUtility.SetObjectReferenceCurve(clip, binding, null)` for PPtr bindings and `clip.SetCurve(..., null)` for float bindings.
- `POST /api/assets/animator-controllers` — creates an AnimatorController asset (includes a default Base Layer).

- `POST /api/assets/animator-controllers/{guid}/layers` — adds a layer with optional weight.
- `POST /api/assets/animator-controllers/{guid}/states` — adds a state with optional motion GUID, speed, and default-state flag.

- `DELETE /api/assets/animator-controllers/{guid}/states` — removes a state by name.

- `PATCH /api/assets/animator-controllers/{guid}/transitions` — updates an existing transition identified by `from`/`to` names.
- `DELETE /api/assets/animator-controllers/{guid}/transitions` — removes a transition identified by `from`/`to` names.
- `POST /api/gameobjects/instantiate` — instantiates a prefab asset into a loaded scene while preserving the prefab connection, with optional `name`, `parent`, and `scenePath`.
- `GET /api/playmode/input/actions` — lists enabled Unity Input System actions in the running game, including action type and effective binding paths.
- `POST /api/playmode/input/perform` — performs a Button InputAction by name through a UnionAir virtual device during Play mode.
- `POST /api/playmode/input/set` — sets Axis, Vector2, and Stick InputAction values on supported virtual Gamepad controls. Values remain active until another set call or Play mode cleanup.
- `GET /api/playmode/ui/elements` — lists active Unity UI and TextMeshPro UI elements that can be targeted during Play mode.
- `POST /api/playmode/ui/click` — clicks a Unity UI `Button` or `IPointerClickHandler` target during Play mode.
- `POST /api/playmode/ui/text` — sets text on a Unity UI `InputField` or TextMeshPro `TMP_InputField` and optionally submits it during Play mode.
- `POST /api/playmode/ui/scroll` — scrolls a Unity UI `ScrollRect` by wheel delta or normalized position during Play mode.
- `POST /api/playmode/ui/value` — sets a Unity UI `Toggle`, `Slider`, `Dropdown`, or TextMeshPro `TMP_Dropdown` value during Play mode.
- `POST /api/playmode/input/pointer` — simulates a mouse click/press/release/move at a screen coordinate through the virtual mouse, spreading the phases across real player frames so the game's own raycast-based hit detection (`PhysicsRaycaster`, `Mouse.current` polling) reacts like it would to genuine input.
- `POST /api/playmode/screen/hittest` — read-only raycast at a screen coordinate (EventSystem raycasters + `Physics.Raycast` from `Camera.main`) reporting what a pointer click there would hit.
- `GET /api/help` — attribute-generated API manifest for LLMs, MCP bridges, and tools that cannot access the documentation directly
- ASP.NET-style attribute routing with `[UnionAirController]` and `[UnionAirEndpoint]` as the source of truth for routing, help, category state, and the EditorWindow endpoint list
- Custom handler discovery under `/api/custom/...`, managed separately in the UnionAir EditorWindow
- Category-level API enablement metadata and endpoint risk reporting for built-in and custom API discovery
- Multi-scene API support: `GET /api/scenes`, `POST /api/scenes/new`, `POST /api/scenes/open`, `POST /api/scenes/unload`, and `POST /api/scenes/active`.
- Custom controller authors can now reuse UnionAir's scene, object reference, GlobalObjectId, and asset reference resolution through the public `UnionAirReferenceResolver` helper.

- `POST /api/assets/open` opens project assets in the Unity Editor, and `POST /api/assets/reimport` reimports individual assets.

In Play mode, reads the composited GameView render texture via reflection, including Screen Space Overlay Canvas UI; falls back to `ScreenCapture.CaptureScreenshotAsTexture()` if reflection is unavailable. In Edit mode, renders the last active Scene View camera. Both endpoints accept optional `width`, `height`, `format`, and `quality` query parameters.

### Fixed

- ObjectRef body fields now distinguish a malformed scalar value from a missing field and return an actionable 400 error with the required object shape. `GET /api/help` also describes the required `target` shape for `POST /api/playmode/ui/click`.
- `GET /api/editor/logs` now matches the `type` filter case-insensitively and returns 400 for unknown values instead of silently returning every log type.
- `POST /api/assets/reimport` now accepts an existing project-relative `assetPath` even when Unity has not registered its main asset type or GUID yet, and returns the GUID assigned by the import.
- Restored compatibility with earlier Unity 6 releases by using the established `FindObjectsByType` overload and object-based asset-label lookup.
- `POST /api/playmode/ui/value` now reports `"clamped": true` when a Slider value was clamped to `[minValue, maxValue]`, instead of silently returning the adjusted value.
- `POST /api/playmode/ui/click` on a non-clickable child (e.g. a Button's `Text` label) now falls back to the nearest ancestor `IPointerClickHandler` instead of returning 422, matching how a real pointer click bubbles through the raycast.
- `POST /api/playmode/ui/text` and `/value` no longer report `success:true` when the reflective TMP `text`/`value` setter or requested submit events cannot be found; they return 500 instead. A missing `RefreshShownValue` now logs a warning instead of being silently skipped.
- Play Mode UI endpoints now recognize subclasses of `TMP_InputField` and `TMP_Dropdown`: TMP types are resolved once per domain load and matched with `IsInstanceOfType` instead of exact type-name comparison. `GET /api/playmode/ui/elements` also lists such subclasses, reports each element's actual component type in `type`, and no longer scans every scene component when looking for TMP elements (skipped entirely when TextMeshPro is not installed).
- Short type names such as `Slider`, `Toggle`, and `Button` no longer resolve to same-named non-matching classes (e.g. `UnityEngine.UIElements.Slider`). Type resolution for `componentPath` references, component add/remove, ScriptableObject creation, and object reference `assetType` now filters candidates by the required base type and keeps scanning instead of returning the first name match.
- `POST /api/playmode/input/perform` now handles Gamepad trigger Button bindings as trigger axis state instead of button bitfield flags, validates Vector2 values as finite numbers, and preserves held Button records when `tap` is called while the same action is pressed.
- `POST /api/playmode/input/perform` now sends full virtual device state for Button actions instead of delta events against bitfield controls, avoiding Keyboard `Key` delta-state failures.
- `POST /api/assets/animation-clips/{guid}/curves` — `objectReferenceCurves` keys now load `Sprite` sub-assets via `AssetDatabase.LoadAssetAtPath<Sprite>` instead of `LoadMainAssetAtPath`. The previous behavior returned a `Texture2D` for Sprite-mode PNGs, causing a type mismatch in `m_Sprite` that crashed Unity during animation preview.
- `DELETE /api/assets/animation-clips/{guid}/curves` — bindings that match existing object reference (PPtr) curves are now removed with `AnimationUtility.SetObjectReferenceCurve(clip, binding, null)` instead of `clip.SetCurve(..., null)`, which silently did nothing for PPtr bindings.
- Hardened JSON string escaping in API responses to correctly encode control characters and prevent malformed JSON output from string fields.
- Normalized non-finite float values (`NaN`, `Infinity`, `-Infinity`) to `null` in JSON responses to keep numeric fields JSON-compliant.
- Replaced non-ASCII dash and arrow characters in API-visible string literals with ASCII equivalents; on machines whose system code page is not UTF-8 (e.g. Japanese Windows), the compiler could misread the BOM-less source files and emit mojibake in `/api/help` summaries and error messages.

### Changed

- Documented that bodyless POST requests are supported and must be framed with `Content-Length: 0` so Windows `HttpListener` does not reject them with 411 before routing.
- `POST /api/editor/refresh` guidance now requires both asset updating and script compilation to become idle, including reconnecting after a domain reload, before clients make dependent calls.
- `POST /api/playmode/input/perform` and `/set` now accept `Map/Action` identifiers. Bare action names remain supported when unique and return 409 with candidate identifiers when ambiguous.
- `POST /api/assets/animation-clips/{guid}/curves` — `curves` is no longer declared as a required body field; `objectReferenceCurves` alone is now a valid payload.
- `POST /api/playmode/input/perform` is now Button-only with `mode` (`tap`, `press`, `release`) instead of `value`; Axis, Vector2, and Stick values use `POST /api/playmode/input/set`.
- Clarified that `GET /api/editor/capture` and `GET /api/editor/capture/image` resize the captured GameView frame in Play mode instead of re-rendering the GameView at the requested `width` and `height`.
- `PATCH /api/gameobjects/components` can now set and clear serialized object references, including scene GameObjects, Components, and assets such as TextAsset.
- Existing scene, search, GameObject, component, and prefab APIs now accept optional `scenePath` targeting for loaded scenes.
- Scene GameObject and Component APIs now expose `globalObjectId` values and accept them as stable target identifiers.
- GameObject, component, camera, and prefab write APIs now use typed object references (`target`, `parent`, `source`) instead of parallel path and ID fields.
- Serialized component object reference payloads now use typed `hierarchyPath`, `componentPath`, and `globalObjectId` references.
- Endpoint metadata now declares Play Mode safety policy, and write APIs are centrally blocked or require both Editor-side Play Mode scene-change permission and `allowWhilePlaying=true` while the Editor is in Play Mode.
- Play Mode scene-object writes now skip scene dirty marking and Undo registration because they are transient runtime changes.
- Endpoint risk metadata now includes `requestDependent` for APIs whose side effects depend on request parameters.
- Endpoint risk metadata now includes `editorState`, and endpoints can override their category risk when they have a narrower side-effect profile.
- Built-in and custom API endpoint lists in the EditorWindow can now expand and collapse by category.
- `SerializedPropertySerializer` utility extracted from `ComponentWriteHandler` and extended with a read direction for reuse across asset and component property serialization.
- `AssetUtils.EnsureDirectory` extracted from `MaterialWriteHandler` as a shared asset file system utility.
